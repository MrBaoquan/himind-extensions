# 专家库与工作流架构审查及调整方案

日期：2026-11-17。状态：审查完成，以下调整为建议方案，尚未实施或发布。

本次读取三个主工作区的当前文件：`himind-extensions`、`项目看板/himind-agent`、`himind-ext-projects`。Agent 基线为 `4e9e6e51475f8cc6bbfcb2eee4a75726b356b3d5`。两个扩展仓均有其他工作留下的未提交内容，相关盘点包含这些候选源码，不能据此宣称已经发布、安装或完成真实任务验收。本次只新增本报告与盘点证据，不修改专家、业务工作流和现有改动。

## 一、结论与问题优先级

1. **高：重复专家没有完成退役。** 项目架构师与系统架构师在源码、开发清单和可选目录中仍是两个身份。之前的调整只把它们归到一个架构职责，优先推荐系统架构师，旧项目架构师继续作为后备；这不是删除，也不是完整的目录治理。
2. **高：专家引用技能不等于运行时具备技能。** Mission 当前固定专家 id/version/digest，并拼接专家方法；技能引用只以 ID 文本进入提示。该链路没有统一解析技能版本、摘要、正文和递归依赖，也没有证明这些技能在每个执行器可用。扩大专家数量前必须补齐这条链路。
3. **高：场景组队能力仍过于通用。** 当前推荐器仅按中英文关键词识别需求、架构、界面、实现、复核五类职责，不是游戏/展项领域规划器。目录只有五个专家包、四类有效专业，产品需求、游戏设计、实时内容和设备集成能力不足。
4. **高：工作流定义与执行尚未完全对齐。** Agent 已复用 WorkflowPackage/WorkflowStore 和底层 WorkflowRunner/LocalRun，但固定流程和 Mission 仍有不同的启动入口与执行责任。带 `roles` 或 `delegate` 的旧流程不因此自动获得专家包绑定、Mission 预算、候选整合及独立验收语义。
5. **高（条件性）：全局激活专家可能污染固定任务上下文。** HiMind AI 的公共配置生成仍调用 `append_active_expert_persona`，工作区没有激活项时会回退全局项；headless Mission/VERIFY 使用同一生成路径。存在有效激活项时可能追加任务 pin 之外的方法。本次没有读取激活状态，不能认定当前任务已经受到影响；需要在 Mission/VERIFY 入口隔离此注入，而不能仅靠独立运行目录。
6. **中：扩展创作契约落后于 Agent。** 扩展仓 Go 工作流清单模型没有 Agent 已有的 roles/role_id/delegate 等字段；打包保留原始文件，但这些字段不受完整语义校验。专家校验器也主要校验身份、正文存在和长度，不验证专业重复、技能闭包或行为质量。仓库检查通过不能替代这些验收。

## 二、冗余专家为什么还在，怎样真正清理

### 已核实的原因

- Agent 的 `docs/expert-library-review-20261116.md` 明确选择“新任务推荐收敛与存储删除分开”，保留旧 ID、发布版本与历史绑定。
- `src/mission/team.rs` 的架构候选顺序仍为 `senior-system-architect`、`project-architect`；只有优先级，没有退役状态或新任务禁选。
- `himind-extensions/extensions.json` 仍登记两个专家，两个源码目录均存在。上轮 Agent main 合并没有同步修改独立的扩展仓。
- `expert.v1` 使用严格字段解析，目前没有 `retired`、`replaced_by` 或专业配置字段，不能直接往 `expert.json` 添加这些键并期望旧 Agent 兼容。

因此，保留历史版本有必要，但让重复身份继续作为普通新建选项没有必要；之前的工作只完成了推荐去重，未完成来源目录、安装目录和历史解析的完整退役。

### 专家逐项处置

| 现有身份 | 建议 | 需要补充 |
| --- | --- | --- |
| `project-architect` 项目架构师 | 从新建、推荐与新增分发移除；保留历史精确读取 | 在目录元数据声明退役及替代身份；历史包可离线解析后，移除活动源码目录和清单登记 |
| `senior-system-architect` 高级系统架构师 | 保留稳定 ID；下一个版本显示名改为“技术架构师” | 架构边界、方案权衡、ADR、数据/接口契约、演进与恢复验证；避免仅靠“高级”暗示质量 |
| `software-engineer` 软件工程师 | 保留并增强 | 实现范围、依赖约束、变更、真实检查、制品与回滚证据；前端/后端/桌面作为专业配置 |
| `senior-ui-designer` 高级 UI 设计师 | 保留稳定 ID；新版本名称收敛为“界面交互设计师” | 引用技能的真实解析、可验证的结构/状态/视觉产出；任务排除项优先于通用规范 |
| `senior-test-engineer` 高级测试工程师 | 保留稳定 ID；新版本名称收敛为“测试质量工程师” | 需求到检查的矩阵、候选摘要、复现条件、缺陷、未覆盖范围和独立复核结果 |

### 退役顺序与完成标准

1. 在现有专家目录/安装注册表的版本化契约增加生命周期元数据，统一事实源；不要把不兼容字段塞进 `expert.v1`。`active` 可用于新任务，`retired` 只用于历史或显式兼容读取。
2. 将旧专家包及正文按原版本、原摘要保存在宿主可解析的不可变存储；确认断网和重启后 `get_pinned` 仍能读到。仅有 Git 历史或任意 archive 目录不满足运行时解析要求。
3. 运行中和历史 Mission 不重绑、不改摘要；已有普通会话投影不得静默换成另一套方法。
4. 新任务 UI/MCP 都过滤退役身份；明确指向退役专家的新任务得到替代提示。已有任务恢复继续使用原 pin。
5. 完成上述兼容验证后，从 `extensions.json` 和活动 `experts/` 删除项目架构师源码，退出工作台新增分发；不卸载仍被任务引用的历史包。

这次审查不把“所有旧包物理消失”作为清理目标。可验收目标是：**新用户只见一个技术架构身份，旧任务仍可按原摘要恢复。**

## 三、协作专家库：五类通用专业，加五类领域专业

专家定义稳定的方法、边界与产出标准；工作流中的职责是本次分工；执行器、服务、模型是运行绑定。用户仍是在职责上选择专家，不应再维护一套同名的“角色库”。同一专家可有多个执行实例，独立复核必须使用不同实例与上下文。

技术栈优先采用专业配置：Web、Rust、Go、.NET、Unity、UNIHper、MyriadBox 不应各复制一整套专家。只有方法和验收显著不同才独立成专家。以下库按需抽调，不是每次启动十个人。

需求入口的组队过程应是：在已授权范围内识别工作区和技术栈，判断任务动作（审查/修复/新增/交付）及软件/游戏/展项场景，选择已安装的团队方法与必要专业，再解析技能和执行绑定。工作区识别可读取实际 manifest、Unity ProjectVersion、VCS 和设备声明，不能仅凭需求中出现“开发”二字选通用工程师。结构化领域元数据和团队配方需增量补充，现有五类关键词规则只保留为保守后备；缺少游戏/展项必要专业时也要明确报缺口。小修复不强加产品、架构或美术，独立复核按交付契约保留。

| 专业身份 | 主要职责与必须交付 | 技能组合与现状 |
| --- | --- | --- |
| 需求与产品设计师（新增） | 目标、用户路径、范围、需求编号、验收条件、待确认问题 | 新增需求分析与验收规格技能；复用工作区上下文。展项脚本和游戏规则通过领域配置补充 |
| 技术架构师（保留现有 ID） | 系统/数据/接口边界、备选方案与理由、ADR、演进与恢复路径 | 架构决策、接口契约、迁移与恢复技能需要整理为可分发包；现有本机技能不能直接视为 Agent 已安装依赖 |
| 软件工程师（增强） | 有界实现、真实检查、变更与可复现交付 | 复用仓内开发类技能；Web/后端/桌面/移动为配置；测试、Git、构建发布技能按项目加载 |
| 界面交互设计师（增强） | 信息架构、任务流、状态、视觉规范、目标设备取证 | 复用界面设计助手、软件界面规范、界面工艺细节；按本次确认的范围选技能与检查 |
| 测试质量工程师（增强） | 风险、最小充分测试矩阵、候选验收、缺陷及未覆盖范围 | 补充通用验证/候选验收技能；桌面 E2E、Web E2E、Unity EditMode/PlayMode、设备恢复作为配置 |
| 游戏设计师（新增） | 核心循环、操作反馈、系统/数值/关卡规则、可玩原型验收 | 新增游戏设计与可玩性验证技能；系统、数值、关卡先采用配置，需求足够复杂再拆独立专业 |
| 实时交互工程师（新增） | Unity/引擎生命周期、场景/资源、输入、存档、性能与目标构建 | 复用 UNIHper 开发助手；补通用 Unity/引擎技能，UPM 在需要时加载。未使用 UNIHper 的项目不得强制依赖它 |
| 技术美术师（新增） | 资源导入、材质/光照/动效、渲染与性能预算、资源交付标准 | 需要新增资源管线、引擎渲染、性能分析技能；媒体下载/制作只作按需工具，不能替代美术质量验收 |
| 展项体验设计师（新增） | 脚本到观众体验、待机/吸引/互动/结束/复位状态、时长与多人场景 | 复用展项开发、展项体验方向技能；把工作台 pid、上传、SVN 等项目集成放适配配置，通用方法不强依赖工作台 |
| 设备集成工程师（新增） | IO/协议、超时/断连/重连、安全停止、现场参数与设备证据 | 复用 IOStudio 调试、视频动作编排；按项目挂载 WebBridge/IODevice/设备能力，真实设备作为独占资源 |

内容密集任务可后续增加“视听内容制作”专业，但本轮不为未来可能需要而预建大量岗位。安全、性能、发布先作为架构/实现/质量的专项技能；确有独立方法、任务量和行为验收后再扩充专家。

### 三类场景的推荐团队与并行方式

| 场景 | 必需专业 | 按需专业 | 可并行工作与收敛点 |
| --- | --- | --- | --- |
| 软件新增功能/修复 | 软件实现、独立质量复核 | 需求、架构、界面 | 同一基线上的架构/界面/风险审查可并行；契约稳定后前后端在隔离目录实现；整合候选再统一验证 |
| 游戏可玩原型 | 游戏设计、实时交互实现、质量复核 | 技术美术、界面、架构 | 玩法规格确认后，逻辑/资源/界面按明确接口并行；同一场景、Prefab、Unity Editor 实例和导入缓存不得互抢；可玩包统一评测 |
| Unity 展项 | 展项体验、实时交互实现、质量复核 | 设备集成、技术美术、架构 | 脚本规格、设备模拟、媒体资源准备可并行；共享 SVN 工作区默认单写；设备联调和最终现场验收显式收敛 |
| H5/MyriadBox 展项 | 展项体验、软件实现、质量复核 | 界面、设备、技术美术 | 前端内容、Provider/协议模拟、素材可在明确接口后并行；目标构建、离线复制启动、触摸/音视频/设备验收在整合候选上完成 |

现实限制必须显示：Mission 当前有限 token/金额上限会把并发降为 1；写隔离只支持严格干净、完整的 Git 根，不能把普通 Unity 的 Library、已初始化子模块或 SVN 工作区宣称为已经支持安全并行写。优先放开只读审查与互不冲突的输出；后续再增加可验证快照/项目隔离策略。

### 专家可用性的宿主契约

新增专家不能止于几段职业提示。每个专家应具备：专业范围/不适用范围、工作阶段、结构化输入输出、必需证据、失败恢复、技能依赖和真实行为样本。

复用现有依赖锁与执行台账，在计划确认前生成解析结果：

- 固定专家及本次专业配置的版本与摘要；专业配置需要新增版本化契约，当前 `expert.v1` 尚不支持。
- 解析实际用到的技能、版本、摘要及正文/引用文件，并解析插件与稳定 Capability 依赖；引用不授予权限。
- 记录执行器对技能交付、工具、模型、联网和访问模式的实际支持；兼容性不能只看 `supported_clients` 字符串。
- 将本任务需要的方法通过受控输入包、正文或可访问文件提供给执行器；不要把全库全文塞进每次提示。确认后固定内容，新增技能或范围变化显示差异。
- Mission/VERIFY 禁止继承普通会话的全局/工作区 active persona，仅使用本任务固定的方法。内置 headless 当前禁用 `tool-skill`，正式 VERIFY 还明确禁止技能探索；不能直接打开动态加载来修复，应预先解析受控技能输入。外部执行器也需核对本地默认上下文和工具边界。
- 区分“有源码”“可打包”“已安装”“依赖就绪”“行为验收通过”；证据绑定专家/技能/执行器/模型版本及任务样本。

UI 专家当前含读屏与 200% 缩放通用要求。本项目已明确不做这两项；本次设计不重新纳入，也不写成延期。应由任务排除项优先级保证不会被专家/技能提示重新引入；不因此擅自删除通用库对其他项目的能力。

## 四、现有工作流与协作任务的关系

推荐统一的用户认知是：**工作流是一套可复用的方法；协作任务是采用某套团队工作流、为一次需求持续执行的实例。**

| 对象 | 存什么 | 不存什么 |
| --- | --- | --- |
| 专家 | 专业方法、交付标准、技能引用 | 当前任务进度、用户路径授权 |
| 技能 | 某类工作的操作知识与能力使用规则 | 第二套任务调度与状态机 |
| 工作流定义 | 职责、步骤/计划规则、依赖、输入输出、验收方法 | 私人会话、机器路径、凭据、已授予权限 |
| 协作任务 Mission | 本次需求、计划、专家/执行器绑定、授权、预算、依赖与交付验收 | 公共可分发方法身份的替代品 |
| Workflow Run / LocalRun | 固定步骤执行或一次专家任务尝试的运行事实 | 第二个 Mission 业务状态所有者 |
| 启动方案 preset | 某个工作流的常用参数 | 可复用团队方法或隐含授权 |

当前已统一：WorkflowPackage 包模型、版本/摘要固定、WorkflowStore 安装存储、底层运行器与 LocalRun。当前未充分统一：创作 Schema、专家/技能依赖、定义类型与启动路由、Mission 和普通 Run 的状态/预算/恢复投影，以及导出后再创建协作任务的完整闭环。不能把目标架构描述成全部已经实现。

目前 Mission 可以从带职责的 Workflow 构建任务方法，也能把完成任务导出为 Workflow。但导出器目前把角色、任务依赖、执行器/模型及检查描述转换为普通 runtime 步骤；没有完整携带专家 pin/技能锁与独立复核的可执行契约。导出提示还保留“遵守本次 Mission……”措辞，需在沉淀时改为对新输入与新授权的引用。导出成功不等于按原团队能力可重复运行。

### 逐项处置矩阵

| 来源与工作流 | 当前形态 | 建议 |
| --- | --- | --- |
| 通用仓：软件发布 | 制品检查、审批、发布与更新解析 | 保留固定流程；作为软件团队任务的交付阶段，不能与需求到实现的“软件交付”混为一条 |
| 通用仓：微信小程序 CI 交付 | 构建、冻结、就绪检查、审批上传 | 保留固定交付流程；对齐 Agent 内相近流程，抽取一份通用 CI 交付来源，按参数配置宿主差异 |
| 通用仓：每日工作日志 | 采集、AI 摘要、写入、归档 | 保留轻量步骤流程，不强加多人指派；AI runtime 步骤不等于专家团队 |
| 通用仓：科技雷达日报 | 采集、AI 解读、报告 | 保留步骤流程；无需额外创建协作团队 |
| 通用仓：素材套图生产（未提交候选） | 确定性批量生产与 AI 复核 | 保留生产管线；先修正生产结果到 `media-kit-batch` Artifact 的接线及等待/失败门禁；多轮创意迭代确有需要时再由团队方法组织 |
| 通用仓：视频转动作 | 多阶段推理、检查、循环与现场确认 | 适合作为内容/设备专家的可调用阶段；若升级团队方法，必须保留既有规格、动作约束与人工现场确认 |
| Agent：软件交付 | 多角色 runtime、质量委派、交付门禁 | 优先对齐 Mission 专家绑定、动态任务及候选验证；避免与通用仓再造一套开发团队流程 |
| Agent：UI 专业打磨团队 | 多角色审查、规划、批准、实现、验证 | 优先迁移为统一团队方法；依赖既有实际设计/质量专家，去掉岗位提示即专家的假象；按任务排除项选择检查 |
| Agent：engine-build | 工程构建/交付阶段流程 | 保留固定流程；复用通用构建/分发能力，不复制专家团队调度 |
| Agent：wechat-miniprogram-delivery / wechat-experience-upload | 本地小程序交付源码，其中前者 ID 已被列为退役 | 前者与通用 CI 包只有 icon/id/name/release_notes 不同，执行结构相同，应清理残留源码维护源；其余按环境与项目适配收敛，兼顾历史 pin |
| 项目仓：展项开发 / 展项 Web 开发 | 固定的开发、检查点、交付与业务同步 | 作为展项团队迁移试点；抽离通用团队方法，pid/SVN/工作台/模板配置保留在项目适配层 |
| 项目仓：展馆预约小程序上传 | 特定项目发布流程 | 留在项目仓，以通用 CI 流程为基础，保留该项目适配 |
| 项目仓：AndX 定制页交付（未提交候选） | 项目特定页面交付 | 留项目仓；按实际需求引用软件团队方法与固定交付流程，不扩大本轮修改范围 |

“统一”应体现为一套定义分类、依赖/权限/结果契约和任务入口，而不是把日报也包装成多人 Mission。固定流程保留轻量执行；团队流程由 Mission 持有业务状态，并复用同一底层步骤运行器。

逐文件核对还发现四项具体问题：

- Go 校验器不只缺角色建模，还会拒绝 `kind=delegate`；JSON Schema 又缺已有 Rust/软件发布包使用的 `capability_alternatives`。当前仓库全绿不能证明 Agent 团队包能走通外部创作链。
- Mission pin 当前主要约束声明角色与可接受执行器；原固定流程的 Approval、Loop、Candidate、Artifact 门禁不会因为“绑定了同一个包”自动变成动态 Mission 的门禁。迁移时必须显式保留，不能仅转换角色名。
- 素材套图候选的复核步骤读取 `media-kit-batch` Artifact，但当前插件终态返回 job/files 等普通字段，未交付 Runner 读取的 `output.artifacts` 元数据；需补产物接线和终态判据。此为未提交候选的静态发现，不代表已发布版本故障。
- 工程工作流助手的示例选择软件发布 `inspect` 入口，却未补该入口需要的 `project_path/product_id`，也没有展示如何传递刚创建的 Checkpoint；迁移中应修示例和真实入口契约，不增加另一套编排器。

### 最小可行统一路径

1. 给工作流增加显式、版本化的执行语义：固定流程、团队方法；混合使用通过有明确父子关系的阶段调用表达。旧包保持既有路径，不能从名字或 `roles` 数量自动判断并改变行为。
2. 对齐 Agent Rust 契约、JSON Schema、Go 创作/校验器和工作流开发技能；目前 roles 的 optional/model、runtime 的 model/permission 等在不同层也需逐字段核对。未知执行字段应明确拒绝或经兼容规则保留，不能静默忽略。
3. 团队方法按输入需求创建 Mission，再进行专家/技能依赖预检、指派、计划与授权确认；固定流程继续调用 Workflow Run。两者共享任务中心的清晰状态投影。
4. 支持团队在明确阶段调用固定交付流程，记录父任务、候选摘要、权限与预算归属、取消传播和恢复关系；一个步骤只有一个状态所有者。此项为目标，不宣称当前已完整支持。
5. 修补 Mission 导出：参数化业务输入、过滤机器专属模型/路径/授权，声明专业需求与技能依赖、必要验证/人工阶段；导入后先算依赖和新运行绑定，再重新确认。保留被排除项，避免沉淀模板偷偷扩大任务范围。
6. 明确每个可分发方法的唯一源码归属。通用方法落 `himind-extensions`，项目集成落 `himind-ext-projects`；Agent 留契约、运行器和必要兼容种子，内置副本不得成为另一套独立演进来源。

工程工作流助手目前仍侧重工程解析、写 Lease、DevelopmentCheckpoint 和固定 `workflow.run.start`，没有覆盖 `mission.intent.create`。长任务推进助手继续负责客户端自身长任务；协作交接技能负责通过 MCP 移交给宿主。需要把交接技能纳入可分发源码及依赖清单，明确三种路由，不能让三个技能分别维护任务状态或同时写同一工作区。

## 五、实施顺序与可验收场景

| 顺序 | 交付 | 退出条件 |
| --- | --- | --- |
| 1 | 专家退役、依赖解析、上下文隔离与创作契约对齐 | 新建只有一个技术架构身份；旧 pin 不变；角色/技能缺失在执行前说明；全局 persona 不进入任务；Schema/运行时一致 |
| 2 | 五类通用专家补强，软件团队方法试点 | 需求到团队、混合 HiMind AI/Codex、候选整合和独立复核均有真实证据 |
| 3 | 增加游戏/展项专业与配置 | 每个新增专业有行为样本；Unity/H5 分别验收；设备与 Editor 资源等待可解释 |
| 4 | 固定交付阶段接入、工作流来源收敛与可复用导出 | 沉淀后换工作区和执行器可重新指派并运行；旧流程仍可恢复；没有复制调度器 |

具体场景：

1. **去重与兼容**：旧任务固定项目架构师 1.0.0 摘要，重启/离线后仍可读取；新建任务和 MCP 目录不再把它作为第二个架构候选；原 ID 不被新内容冒名覆盖。
2. **软件开发**：输入需求、仓库路径和授权范围，推荐必需专家；产品/架构/UI 仅按需要加入；前后端隔离并行，最终整合候选真实检查，由独立质量实例验收。
3. **跨执行器技能一致性**：同一 UI 专家和技能版本分别在 HiMind AI/Codex 执行，台账可回读实际输入摘要、技能正文来源、工具就绪情况；缺失技能不能因提示写了 ID 而通过。
4. **游戏原型**：玩法、技术美术、实现分工可追踪；共享场景/Prefab/Editor 冲突有等待理由；可玩包验证输入、存档/复位和性能目标，不能只提交设计文档算游戏完成。
5. **展项交付**：同一脚本分别走 Unity 与 H5 配置，追踪需求到截图/演示/测试证据；断网、设备断连和待机复位有检查；未提供真实设备时对应项保持未验证。
6. **SVN/非干净工作区**：不冒称 Git worktree 并行，明确降级；只读规格与资源准备仍可独立进行；共享源码单写，不丢失人工修改。
7. **沉淀与分发**：已完成团队任务导出后，在另一个目录重新创建，不能带出旧对话、机器路径、私有服务、授权或历史通过标记；按新专家/技能/执行器预检与新授权运行。
8. **轻量流程与恢复**：日报仍可直接跑固定流程；团队交付调用发布阶段只出现一个审批/一个副作用；取消、宿主重启、预算追加继续保留父子状态与候选证据。
9. **方法上下文隔离**：激活与任务无关的普通会话专家，再分别启动固定专家的交付和 VERIFY；输入台账中不出现该 active persona，固定专家/技能摘要保持一致；全局设置改变不影响已确认任务。

本次已执行 `go run ./tools/cmd/himind-repo-check`：44 个登记扩展通过当前仓库规则。此结果不验证专家专业质量、跨执行器技能加载或上表新方案。工具对专家提示未出现在 GitHub catalog，不代表工作台专家目录未发布：专家本来走独立工作台渠道，不能把 GitHub catalog 缺席当成故障。
