# 工作日志「当前工作台」方案

> 目标：打开工作日志后，能一眼看清当前正在推进哪些项目、各自优先级、是否完成、卡在哪里、下一步做什么，以及最近实际投入了多少时间。
>
> 延伸方案：`docs/work-log-ai-planner-design.md`（工作项、预计耗时、AI 日程规划、计划与实际复盘）。
> 实现口径（0.15.0）：当前工作台默认只展示最近 14 天有活动的项目；更早的项目进入历史，不计入「正在推进」。阶段与完成进度由最近日志、下一步和工作状态推断，界面标注为「推断」，用户可在编辑中覆盖。

## 1. 现状与差距

现有工作日志已经具备：

- 按日记录条目：项目、功能、展项、工时、完成项、阻塞、下一步、引用。
- 日历回看、报告、工时表、项目推进记录。
- `projects.json` 项目登记表：名称、别名、类型、路径映射、`active/archived` 状态。
- 采集、AI 总结、日报、周报/月报的完整链路。

但现有「项目」页本质上仍是**历史回看**：

- 只能看到条目时间线、条目数、活跃天数、工时合计。
- 项目状态只有 `active/archived`，无法表达「进行中 / 受阻 / 待验收 / 已完成 / 暂停」。
- 没有优先级、目标、完成度、目标日期、下一步计划、完成摘要。
- 条目的 `next`、`blockers` 分散在每天日志里，需要逐条翻看。
- 无法快速回答「现在最该推进什么」。

## 2. 核心设计原则

### 2.1 日志是事实，工作台是意图

- **日志条目**记录已经发生的事实：做了什么、花了多久、产出了什么。
- **项目工作状态**表达当前意图：优先级、是否完成、下一步计划、目标日期。
- 不根据日志文本自动推断并静默修改项目状态，避免把「今天提到完成」误判成「项目已完成」。
- 自动信号只做提示和建议，最终状态由用户确认。

### 2.2 项目级优先，功能级按需

本期以「项目」为主视角，满足当前诉求；功能/展项仍作为项目详情里的维度。下一步计划用轻量清单表达，不引入完整任务管理系统，避免与 Jira/Linear/工作台重复。

### 2.3 不伪造完成度

「是否完成」由明确状态回答。进度百分比可选：

- 有下一步清单时，展示「计划完成度 = 已完成步骤 / 总步骤」。
- 没有清单时，不强行计算百分比，展示「最近活动 + 未完成步骤数」。
- 如用户需要，可手工填写项目进度百分比，但界面明确标注为手工进度。

## 3. 推荐的用户界面

### 3.1 新增一级页签「当前工作」

顶部页签调整为：

`当前工作 | 日历回看 | 报告 | 工时表 | 项目`

建议将「当前工作」设为默认落地页；日历回看保留原能力。默认只展示最近 14 天有日志的项目，更早的项目折叠到「其他项目」，避免把历史项目都当成未完成工作。阶段与进度优先使用用户手工值，否则由最近日志、下一步和项目状态智能推断，并在界面标注推断来源。

页面结构：

```text
┌──────────────────────────────────────────────────────────────┐
│ 当前工作                         [列表/看板] [筛选] [刷新]   │
├──────────────────────────────────────────────────────────────┤
│ 进行中 5   受阻 1   待验收 2   本周完成 3   本周投入 26.5h   │
├──────────────────────────────────────────────────────────────┤
│ 需要处理：X 项目受阻 · Y 项目 7 天无日志                     │
├──────────────────────────────────────────────────────────────┤
│ 今日聚焦                                                     │
│ ┌────────────────┐ ┌────────────────┐ ┌────────────────┐     │
│ │ P0 项目 A      │ │ P1 项目 B      │ │ P1 项目 C      │     │
│ │ 进行中  60%    │ │ 受阻           │ │ 待验收         │     │
│ │ 下一步：...    │ │ 阻塞：...      │ │ 下一步：...    │     │
│ │ 2h · 今天      │ │ 0.5h · 昨天    │ │ 4h · 10-18     │     │
│ └────────────────┘ └────────────────┘ └────────────────┘     │
├──────────────────────────────────────────────────────────────┤
│ 全部进行中                                                   │
│ P0  项目 A   进行中   60%   下一步 2 项   今天更新   [编辑] │
│ P1  项目 B   受阻     --    阻塞 1 项     昨天更新   [编辑] │
│ P2  项目 D   进行中   40%   下一步 3 项   3 天前     [编辑] │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 项目卡片/行

每张卡片至少展示：

- 项目名、项目类型、展项（可选）。
- **状态**：待开始 / 进行中 / 受阻 / 待验收 / 已完成 / 已暂停。
- **优先级**：P0 / P1 / P2 / P3，带颜色条。
- **下一步**：最多展示 2 条未完成项，可直接勾选完成。
- **最近动态**：最近一次日志日期、最近一条标题。
- **本周投入**：最近 7 天工时。
- **目标日期**：剩余天数或已逾期。
- **提示**：N 天无日志、阻塞未处理、全部步骤已完成待确认。

快捷操作：

- 改状态（下拉或按钮组）。
- 改优先级。
- 编辑下一步 / 阻塞。
- 标记完成。
- 打开项目详情。

### 3.3 项目详情页

在现有「推进记录」上方增加「当前状态」面板：

```text
项目 A  [P0] [进行中] [60%] [目标 10-30]
目标：完成工作台第一版
下一步：
  ☐ 设计项目状态数据结构
  ☐ 实现项目看板接口
  ☑ 完成现有项目页调研
阻塞：等待设计确认
最近动态：今天 · 完成工作台方案
本周投入：6.5h
[编辑状态] [标记完成] [写一条日志]
```

下面继续保留现有按日期/展项的功能推进时间线。

### 3.4 已完成区

- 默认折叠，显示「本周完成 N 个」。
- 展开后按完成时间倒序。
- 完成项目保留在「项目」页，不直接归档。
- `archived` 只表示从日常视图隐藏，不表示完成。

## 4. 数据模型

### 4.1 扩展 `projects.json`，不新增数据库

继续由 `work-log` 插件作为唯一写入者，在 `projects.json` 中增加 `work` 对象：

```json
{
  "schema_version": "work-log-projects.v2",
  "updated_at": "2026-10-19T10:00:00+08:00",
  "projects": [
    {
      "id": "pj-abc123",
      "name": "项目看板",
      "aliases": [],
      "description": "项目状态与工时看板",
      "status": "active",
      "kind": "平台产品",
      "source": "local",
      "paths": [],
      "exhibits": [],
      "work": {
        "state": "in_progress",
        "priority": "P1",
        "progress": 60,
        "goal": "完成当前工作台第一版",
        "target_date": "2026-11-15",
        "next_steps": [
          {
            "id": "ns-001",
            "text": "设计项目状态数据结构",
            "done": false,
            "due": "2026-10-22",
            "source": "manual",
            "created_at": "2026-10-19T10:00:00+08:00",
            "completed_at": ""
          }
        ],
        "blockers": ["等待设计确认"],
        "completed_at": "",
        "completion_summary": "",
        "updated_at": "2026-10-19T10:00:00+08:00"
      },
      "created_at": "2026-09-01T09:00:00+08:00",
      "updated_at": "2026-10-19T10:00:00+08:00"
    }
  ]
}
```

### 4.2 字段语义

| 字段 | 说明 |
| --- | --- |
| `status` | 登记表生命周期，保持 `active/archived`，不复用为工作状态 |
| `work.state` | `planned` / `in_progress` / `blocked` / `review` / `done` / `paused` |
| `work.priority` | `P0` / `P1` / `P2` / `P3` |
| `work.progress` | 可选手工进度，0-100；为空时不展示百分比 |
| `work.goal` | 当前阶段目标，一句话 |
| `work.target_date` | 目标完成日期，可空 |
| `work.next_steps` | 下一步清单 |
| `work.blockers` | 当前阻塞，人工维护 |
| `work.completed_at` | 进入 `done` 的时间 |
| `work.completion_summary` | 完成摘要 |
| `work.updated_at` | 工作状态最近更新时间 |

状态含义：

- `planned`：已登记，尚未开始。
- `in_progress`：正在推进。
- `blocked`：当前受阻，需要外部条件或决策。
- `review`：开发完成，等待验收/确认。
- `done`：已完成。
- `paused`：主动暂停，不是完成。

优先级含义：

- `P0`：最高，今天/本周必须推进。
- `P1`：高，本周重点。
- `P2`：中，正常排期。
- `P3`：低，有空再做。

### 4.3 兼容与迁移

- `schema_version` 升级为 `work-log-projects.v2`。
- `work` 缺失时按默认值补齐：
  - 有历史条目的 active 项目：`state=in_progress`、`priority=P2`。
  - 无历史条目的 active 项目：`state=planned`、`priority=P2`。
  - `archived` 项目保持隐藏，不进入当前工作台。
- 只做读时补默认值和一次性落盘，不修改任何每日日志文件。
- 备份/恢复、项目导出/导入需包含 `work` 字段，并保持对旧格式的兼容。

## 5. 后端能力设计

### 5.1 新增只读能力 `work-log.project.board`

返回当前工作台所需的聚合数据，避免前端多次扫描和自行推断：

```json
{
  "summary": {
    "in_progress": 5,
    "blocked": 1,
    "review": 2,
    "done_this_week": 3,
    "minutes_this_week": 1590
  },
  "attention": [
    {"project_id": "pj-...", "name": "项目 X", "reason": "blocked"},
    {"project_id": "pj-...", "name": "项目 Y", "reason": "stale", "days": 7}
  ],
  "focus": ["pj-...", "pj-..."],
  "projects": [
    {
      "id": "pj-...",
      "name": "项目 A",
      "kind": "平台产品",
      "state": "in_progress",
      "priority": "P0",
      "progress": 60,
      "goal": "...",
      "target_date": "2026-11-15",
      "next_steps": [],
      "blockers": [],
      "last_date": "2026-10-19",
      "days_since_activity": 0,
      "minutes_7d": 390,
      "entry_count": 42,
      "stale": false
    }
  ]
}
```

排序规则：

1. 需要处理（`blocked`、严重 stale）置顶。
2. 今日聚焦取 P0/P1 且未完成的项目，最多 3 个。
3. 其余按优先级、目标日期、最近活动时间排序。
4. `done` 和 `archived` 默认不进入进行中列表。

### 5.2 新增写能力 `work-log.project.work.update`

采用 patch 语义，只更新显式传入的字段：

```json
{
  "project_id": "pj-abc123",
  "patch": {
    "state": "in_progress",
    "priority": "P0",
    "progress": 60,
    "goal": "完成当前工作台第一版",
    "target_date": "2026-11-15",
    "blockers": ["等待设计确认"],
    "next_steps": [
      {"id": "ns-001", "text": "设计数据结构", "done": true}
    ]
  }
}
```

规则：

- `next_steps` 整体替换；缺 `id` 的步骤由服务端生成稳定 ID。
- `state=done` 时自动写 `completed_at`，可同时写 `completion_summary`。
- 从 `done` 重新打开时清空 `completed_at`，并记录 `reopened_at`（可后续扩展）。
- 校验状态、优先级枚举和进度范围。
- 所有写入继续使用现有 `lockRoot`，保证与日志写入、备份恢复互斥。

### 5.3 可选便捷能力

- `work-log.project.next_step.toggle`：只切换某一步骤完成状态，避免前端整组回写。
- `work-log.project.complete`：完成项目并可选写入一条完成日志，减少前端编排。
- `work-log.project.work.list`：按状态/优先级筛选，供 Agent 查询。

MVP 至少需要 `work-log.project.board` 和 `work-log.project.work.update`。

### 5.4 派生信号

不落盘、按需计算：

- `last_date`：最近一条日志日期。
- `days_since_activity`：距今天数。
- `minutes_7d` / `minutes_30d`：近 7/30 天工时。
- `entry_count` / `active_days`：沿用现有统计。
- `stale`：`in_progress/review` 且超过 3 天无日志；超过 7 天标记为严重。
- `plan_completion`：已完成步骤 / 总步骤。
- `recent_next`：最近 3 条日志里的 `next`，去重后作为「建议下一步」，由用户点击采纳，不自动写入。

## 6. 关键交互流程

### 6.1 日常查看

1. 打开插件默认进入「当前工作」。
2. 先看顶部摘要和「需要处理」。
3. 看「今日聚焦」3 个项目。
4. 点击卡片进入项目详情，查看时间线和完整下一步。

### 6.2 更新状态/优先级

1. 卡片上直接改状态或优先级。
2. 调用 `work-log.project.work.update`。
3. 局部刷新卡片，不整页重载。
4. 记录 `work.updated_at`。

### 6.3 维护下一步

- 详情页新增/编辑/删除/勾选下一步。
- 勾选后即时保存。
- 全部步骤完成时，提示「下一步已全部完成，是否将项目标记为待验收或已完成？」但不自动改状态。
- 可从最近日志的 `next` 一键采纳为计划步骤。

### 6.4 标记完成

1. 点击「标记完成」。
2. 弹窗填写完成摘要（可从最近条目的 `outcomes` 预填）。
3. 可选「同时写一条完成日志」，默认勾选。
4. 确认后：
   - 项目 `state=done`，写入 `completed_at`。
   - 如果勾选，写入一条工作日志条目。
   - 从进行中列表移到已完成区。
5. 重新打开时记录一条可选日志，并恢复为 `in_progress`。

### 6.5 Agent 查询与更新

- 用户问「现在有哪些项目在推进 / 哪个最优先 / 下一步是什么」：调用 `work-log.project.board` 汇总回答。
- 用户说「把 A 标成 P0 / 标记完成 / 下一步加 X」：调用更新能力，写入前复述变更。
- 日志总结发现阻塞、完成迹象或下一步：只提建议，不静默改项目状态。
- 日报/周报可增加「项目状态快照」段落，但状态变更仍需用户确认。

## 8. 实施阶段

### Phase 1：MVP（建议先做）

- `projects.json` v2 与迁移。
- `work-log.project.board` 只读能力。
- `work-log.project.work.update` 写能力。
- 「当前工作」页签：摘要、需要处理、今日聚焦、进行中列表。
- 状态/优先级/下一步/阻塞/目标日期/完成操作。
- 项目详情顶部状态面板。
- 测试与技能文档。

验收标准：

- 打开插件即可看到所有进行中项目及状态、优先级、下一步、最近活动、本周工时。
- 改状态/优先级/勾选下一步后刷新仍保留。
- 标记完成后从进行中移除，进入已完成区，并可选择写完成日志。
- 旧 `projects.json` 和旧日志无需手工迁移即可正常加载。
- 备份/恢复后新字段不丢失。
- Agent 可通过能力查询和更新，不静默改状态。

### Phase 2：效率增强

- 看板视图（按状态分列）与拖拽改状态。
- 「从最近日志采纳下一步」。
- 项目状态快照写入日报。
- stale / 逾期提醒。
- 计划完成度与手工进度双口径。

### Phase 3：规划增强

- 每周项目复盘工作流：AI 读取工作台 + 一周日志，生成优先级和下一步建议，用户确认后写入。
- 功能/展项级工作项（仅当确实需要时）。
- 跨项目依赖、里程碑、提醒。
- 与工作台项目状态双向同步（需明确冲突解决策略）。

## 9. 风险与取舍

| 风险 | 应对 |
| --- | --- |
| 手工状态长期不更新，看板失真 | 显示最近更新时间、无日志天数；每周复盘提示；不自动改状态 |
| 自动从日志推断完成导致误判 | 只做建议，必须用户确认 |
| `status` 与 `work.state` 语义混淆 | `status` 仅表示登记生命周期，工作状态独立 |
| 进度百分比虚假精确 | 默认不展示百分比，优先展示计划完成度 |
| 变成完整任务系统，维护成本高 | 本期只做项目级状态 + 轻量下一步清单 |
| 迁移破坏旧数据 | 读时兼容、一次性补默认值、备份/恢复测试 |
| 前端缓存旧资源 | 同步提升 `app.js/app.css` 版本后缀 |

## 10. 推荐结论

建议采用「**显式项目状态 + 自动活动信号 + 轻量下一步清单**」的混合方案：

- 项目状态、优先级、下一步由用户维护，保证可信。
- 最近活动、工时、无日志天数由日志自动计算，保证及时。
- 新增「当前工作」作为默认页，回答「现在做什么、是否完成、优先级、下一步」。
- 不把工作日志改造成重型任务系统，保持本地、轻量、可回看。

这是改动可控、对现有数据兼容、且能直接解决当前诉求的方案。Phase 1 即可满足核心需求。
