## 6. 先实测，再放量

1. **视觉能力探针**：每个候选模型发 1 张 64×64 测试图，确认是否接受图片输入（成本可忽略）。
2. **小批 pilot**：30 个资产（10 视频 + 10 图片 + 10 音频），记录真实 token、耗时、失败率。
3. **外推**：按 pilot 单资产成本 × 总量，更新本文件后再批准大批量。
4. 50 万级优先本机打标/抽样，不默认全量调用付费视觉模型。

## 7. DeepSeek V4.1 Flash 实测（2026-10-31）

- 服务：`custom:deepseekv41f`（vectide.cn，OpenAI Responses）。
- 512×512 PNG：386 input / 111–224 output，约 497–610 tokens，8–42s。
- 320px 网格缩略图 JPEG：约 672 tokens，UI 端到端 60s 内返回。
- 真实航拍帧结果：正确识别“高楼玻璃幕墙外清洁工人、吊板、安全绳、城市绿化/道路”，标签 8 个、质量 3。
- 单资产按 600–700 tokens 估算：363 个约 24 万 tokens；按 $0.15/$0.60 每百万 token 约 **$0.04–0.06**。
- 注意：
  - 激活服务 `himinddsh` 当时余额不足（402），需换有余额的服务；
  - `custom:deepseek-xlcx` 有一次把红蓝几何图描述成“空白”，稳定性待观察；
  - `opencode-go` 需要 `x-opencode-session` 头，暂未接入；
  - 单张延迟可达 8–60s，批量打标应做成后台作业，不能阻塞 UI。

## 8. 输入参数优化实测（2026-10-31）

| 模式 | 输入 | 输出 | 总 token | 延迟 |
| --- | ---: | ---: | ---: | ---: |
| `full`（标签+描述+质量） | 386 | 111–224 | 497–610 | 8–42s |
| `fast`（仅标签） | 389 | 114 | 503 | 7s |
| `fast + reasoning_effort=none` | 389 | 105 | 494 | 5s |

- 图片缩到 512 与 1024 的输入 token 差异不大，主要成本在提示词、输出与推理 token；
- 批量用 `fast` 可省掉描述与质量输出，单张约省 100–150 tokens；
- 真正的吞吐提升来自：
  1. 相似组只打代表帧（10 条入选可能只需 3–6 次调用）；
  2. 结果缓存，重复操作 0 调用；
  3. 并发 2–4，但受网关延迟/限流约束；
  4. 后台作业，避免界面卡在单次调用上。

## 10. 后台批量实测（2026-10-31）

Agent 侧 `media.ai.tag.batch.start/status/cancel/resume/list`，作业落盘在
`agent_home()/media-ai-jobs/<job_id>.json`。

| 场景 | 组数 | 成功/失败 | tokens | 说明 |
| --- | ---: | --- | ---: | --- |
| fast，2 组 | 2 | 2/0 | 1,129 | 543 + 586，单张约 560 |
| full，10 组（关窗后台跑） | 10 | 10/0 | 53,585 | 平均 5,358；单张最高 14,201 |
| full + reasoning_effort=none，2 组 | 2 | 2/0 | 30,748 | 一张 636，一张 30,112 |

结论：

- **fast 是批量默认**：单张约 560 tokens，结果稳定；
- **full 成本不可预测**：同一批里出现过 636 与 30,112 的极端差异，网关对
  `reasoning_effort=none` 并不是每次都生效，单张花费可差 50 倍；
- 因此批量只按 `fast` 估算，`full` 必须靠预算闸门兜底，UI 里也标注“更贵”；
- 预算闸门按 `ai_tag_cache` 的实际 token 累计（单次 $2 / 每日 $5 / 每月 $20），
  提示词变化不会重复计费，只有真正调用过模型才写缓存与计费；
- 关窗/重开视图甚至 Agent 重启后，作业仍在后台跑，重连时按精选集恢复进度。
