# MCP 使用体验反馈

## 用途定位

本技能帮助用户在使用 AI 工具（如 ZCode、Claude Code、Cursor、Gemini CLI 等）通过 HiMind Agent MCP 完成真实任务后，把"哪里用得不顺手"沉淀为**结构化、可被 AI 快速定位和理解的优化需求项**，供后续工具（himind-agent 服务端、MCP 工具层、AI 客户端适配层）优化解决。

产出物是两类内容：

1. **使用体验复盘**：整体评价 + 四维度评估（友好性 / 合理性 / 便捷性 / 阻碍性）+ 问题清单。
2. **优化需求项**：每条需求含问题描述、复现场景、现状与期望行为、验收标准、优先级、影响面、证据片段，AI 可以拿着需求项直接定位到具体工具或能力并开始修复。

## 触发场景

- 用户说"总结一下这次使用体验怎么样""有什么不顺的地方""帮我记录下优化点""提个需求给开发"。
- 任务完成后，AI 发现工具存在以下情况时主动提示并询问是否复盘：
  - 返回结果与参数语义不符（例如过滤参数不生效、排序不符合预期）；
  - 结果被截断、分页缺失或字段不全，需要多次绕行才能拿全数据；
  - 报错信息无法定位根因（无错误码、无重试建议、无操作指引）；
  - 缺少"一步到位"的能力，需要多步手工拼接；
  - 接口返回了大量与任务无关的数据，挤占了上下文导致有效信息丢失；
  - 名称、字段或命名与预期不一致，容易误用；
  - 调用超时、权限报错、参数校验失败等阻碍任务完成。

## 工作流程

### 第 1 步：确认复盘范围

向用户确认（或从对话上下文推断）：

- 复盘哪一次任务（例如"查询项目展项列表"），使用的客户端是什么；
- 涉及哪些 MCP 工具（列出工具名，如 `business.exhibit.list`）；
- 产出方式：仅在对话中输出报告，还是同时写入工作区文件（写文件需用户确认路径，默认 `.agents/skills` 外的 `docs` 目录或用户指定目录）。

### 第 2 步：收集客观体验证据

只记录**真实发生过**的事实，每一条证据都要能对应到具体调用：

| 证据类型 | 记录要点 | 示例 |
| --- | --- | --- |
| 调用参数 | 工具名、关键参数及值 | `project: "项目测试用例"`, `page_size: 100` |
| 返回特征 | 是否截断、是否为空、是否缺字段、量大或小 | 返回 86KB，被模型侧截断为 50KB |
| 错误信息 | 原始报错、错误码、isError 标记 | `capability not found: business_exhibit_list` |
| 耗时/次数 | 一次成功或多次重试、翻了几页 | 翻页 10 次才取回全部记录 |
| 绕行路径 | 发现缺陷后如何绕过完成的 | 改为翻页全量拉取后本地过滤 |

不要把"AI 自己的选择"（例如选了某个客户端）算作工具缺陷；证据不足时应标注"待重试确认"。

### 第 3 步：按四维度评估

对每个发现的现象，用"评价 + 关键现象"记录：

- **友好性**：参数是否语义化、返回是否结构化、命名是否易懂、错误是否给出解决方向。
- **合理性**：字段语义是否正确、过滤/排序/分页是否真正生效、权限与风险等级是否匹配、默认值是否合理。
- **便捷性**：是否缺个字段就得绕行、是否缺少组合查询/聚合能力、常用操作是否需要多步拼接。
- **阻碍性**：是否超时、是否必须人工介入、报错是否可定位、截断后是否有恢复手段。

评价维度统一用三档：**好（无问题）/ 一般（可用但别扭）/ 差（阻碍任务）**。

### 第 4 步：问题分类

每个问题归为四类之一：

- **缺陷**：行为与参数语义或文档承诺不符，属于 Bug。
- **不便**：功能可用，但需要绕行或理解成本高。
- **优化**：现有能力可以更好用（返回裁剪、字段补充、错误改进）。
- **增强**：缺少新能力（新的过滤项、聚合视图、批量操作等）。

### 第 5 步：生成结构化需求项

按下方模板逐条生成，字段必须填全（无内容填"无"），并遵循：

- `tool` 写 MCP 工具/能力 ID（如 `business.exhibit.list`、`exhibit.workspace.status`），便于开发者 grep 定位；
- `evidence` 粘贴原文片段（参数与返回 JSON 摘要、报错文本），不得改动原值；
- `acceptance` 写成可判定真假的语句（"当…时应…"，可以勾选验收）；
- 同一问题拆成一条需求，不要合并多问题；同一工具多个问题按条拆分。

### 第 6 步：输出报告

对话中输出完整报告，推荐结构：

```
# MCP 使用体验复盘报告

## 复盘范围
（任务、客户端、工具清单、日期）

## 整体评价
（一段话结论：总体上是否完成、体验是否顺畅、最主要的问题）

## 四维度评估
| 维度 | 评价 | 关键现象 |
| --- | --- | --- |
| 友好性 | 一般 | ... |
| 合理性 | 差 | ... |
| 便捷性 | 一般 | ... |
| 阻碍性 | 差 | ... |

## 问题清单（按优先级）
| ID | 标题 | 类型 | 工具 | 优先级 |
| --- | --- | --- | --- | --- |

## 需求项明细
（第 5 步的 JSON 模板逐条列出）

## 建议处理方式
（建议转交哪个环节：工具层 / 客户端适配层 / 文档说明，是否可先本地规避）
```

若用户确认写入文件，保存在工作区内（默认 `docs/mcp-feedback/<yyyy-MM-dd>-<客户端>-<任务主题>.md`），并报告保存路径。

## 需求项模板

```json
{
  "id": "REQ-001",
  "title": "",
  "type": "缺陷 | 不便 | 优化 | 增强",
  "tool": "mcp 工具或能力 id，如 business.exhibit.list",
  "priority": "高 | 中 | 低",
  "problem": "问题描述：现象 + 对使用者的影响",
  "context": "使用场景：常态还是偶尔、哪个客户端、什么任务",
  "current": "现状行为：工具实际返回或表现",
  "expected": "期望行为：希望工具怎么做",
  "acceptance": ["验收标准1", "验收标准2"],
  "impact": "影响面：谁受影响、大概频次",
  "evidence": "证据：调用参数摘要 + 返回/报错原文片段",
  "suggestion": "建议方案（可选，留给开发参考）",
  "source": "来源：会话主题与日期（可选）"
}
```

## 风险门禁与边界

- **只写事实**：未验证的现象不纳入需求项；宁可标注"待确认"也不要编造。
- **不落敏感信息**：证据片段中不得包含 Token、Cookie、密码或内部凭据，引用时脱敏。
- **不写可执行内容**：报告只生成 Markdown/JSON 文本；不生成脚本安装包或修改工具配置。
- **不动业务数据**：不自动调用 `business.requirement.create` 等写入类能力创建需求；只输出需求项，由用户决定转交方式。
- **文件范围**：报告文件只在当前工作区内写入，路径需用户确认；不得写工作区以外目录。
- **如实区分**：AI 客户端侧的截断/上下文限制不等同于服务端缺陷，报告需注明问题归属（工具层 / 客户端适配层 / 文档说明）。

## 后续动作

- 需求项可直接粘贴给工具开发/维护人员；如本机配置了对应业务能力，用户确认后再创建正式需求。
- 若干问题可本地规避时，在报告中先给出规避办法（例如"改用全量列表过滤"），保证当前任务不被卡住。
