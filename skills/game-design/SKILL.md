# 玩法规则与验证

## 输入与边界

输入玩家群体、平台和输入方式、单局时长、体验目标、内容/研发约束与已有原型。设计可用于任意引擎，不强制 Unity 或 UNIHper。只有题材、美术或剧情稿时不能宣称已有玩法。

## 方法

1. 用一句可验证假设描述乐趣来源，再画“观察 → 决策 → 行动 → 反馈 → 资源/状态变化”的核心循环。写胜败、退出和重开条件，识别没有有效选择的等待。
2. 规则表包含状态、触发、合法动作、前提、数值公式及单位、反馈时机、结果和冲突优先级。连续输入、暂停恢复、死亡/结算同帧等边界必须可确定。
3. 建经济与数值小样本：来源/消耗、成长曲线、随机分布或种子。至少推演起始、中段、极端三组；检查资源能否无限增长、负值、必胜策略和不可恢复死局。
4. 关卡按引入、练习、变化、检验组织；每个挑战写能力门槛、提示、失败成本和退出路径。不要用增加敌人血量代替所有难度变化。
5. 制作最小可玩闭环，先用占位资源验证决策和反馈；技术实现转交工程方法。记录原型版本、输入设备、观察任务、样本数与测量规则。
6. 试玩区分观察和解释，记录首次理解时间、完成/失败、重试与退出、主观反馈。样本少时报告局限，不把作者演示当玩家测试。一次迭代优先改变一个主要假设并前后对比。

## 输出与验收

交付核心循环、规则/数值表、关卡节拍、原型验收清单和试玩记录。通过条件：玩家能从开始走完一次成功或失败并重开；规则无未定义冲突，极端数值无不可恢复死局；体验假设有目标玩家观察支持或标为未验证。体验指标的阈值、样本目标在试玩前确定，不用完成后的结果倒定门槛。

## 受阻与恢复

无可玩版本先交规则规格和验证计划，保留“可玩性未验证”。表现不达标回到观察定位是理解、决策、反馈还是难度问题，简化循环后重测；不要用新增系统掩盖原循环无法成立。随机性问题保存种子及输入序列。
