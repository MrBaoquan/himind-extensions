# 需求与验收规格

## 输入与边界

读取任务目标、使用者及场景、已有流程、约束、交付期限和明确排除项。区分原话、现场事实、推断；资料缺失先记录假设，只有会改变范围或验收结论的未知项阻塞对应条目。纯实现细节、架构选型和视觉风格交给相应方法，不借规格扩大授权。

## 方法

1. 写出可观察的目标：谁在什么情境完成什么任务，现状基线是什么，如何衡量改善。没有业务基线就写待采集项，不编造提升比例。
2. 按主路径、替代路径和失败恢复拆解场景；标注触发者、前置状态、输入、结果、异常及数据归属。删除不能追溯到目标的功能。
3. 给需求稳定编号 R-001，记录来源、优先级、依赖、范围内/外。P0 是无法完成核心任务或造成不可接受损失，P1 是本次承诺，其余放候选，不把全部条目设为最高优先级。
4. 为每条承诺需求写 AC：前提 → 操作 → 可观察结果 → 判据 → 证据方式。例如断网保存：已有草稿时断网点击保存，保留草稿并展示失败与重试入口；恢复网络重试仅生成一条记录，以操作录像和记录 ID 核对。
5. 性能、隐私、离线、目标设备等约束写测试环境与阈值；“快”“好用”不能作判据。阈值缺失可以提出建议值，但标为假设，不能当作已达成目标。
6. 将需求链接到交付物和验证项；新增需求必须列出对成本、依赖和验收矩阵的影响，沿用原编号，禁止悄悄挪动验收目标。

## 输出与验收

输出目标及基线、场景图或步骤、范围清单、需求/AC/证据追踪表、假设与待决问题。追踪表列为：需求 ID｜来源｜优先级｜前提与动作｜预期和阈值｜验证方法｜依赖｜状态。

通过条件：本次 P0/P1 全部有来源、AC 和证据方式；每个失败路径有可执行恢复；排除项没有被隐含依赖带回；不存在互相矛盾的 AC。规格就绪不代表功能通过。

## 受阻与恢复

目标冲突时列出冲突条目及最小待决问题，继续处理独立条目。需求变化保留差异及受影响 AC，重新核对依赖和验证，不把上一版通过结果移植到新行为。资料不足的条目保持待定，不能用“已确认”掩盖假设。
