# 软件界面规范

面向软件开发的界面规范：把界面质量要求写成可判定、可验收的约束，并据此审查界面、给出整改方案。适用于 Web、桌面客户端（含 Electron / Tauri / WebView2 一类混合应用）、移动端以及设计稿评审。

## 适用范围

覆盖界面层，UI 与 UX 合并定义：

- UI 侧：视觉层次与间距、布局与响应式容纳性。
- UX 侧：信息架构与导航、内容与文案、交互与状态反馈、无障碍与包容性。
- 一致性与规范对齐贯穿两者。

不拆成两套规范：同一个界面问题，"看起来乱"与"用起来不通顺"常常同源，拆开会产生两份重叠又互相打架的规则。

不覆盖：业务逻辑、数据模型、接口契约、性能架构、安全策略。审查中发现这类问题，记录并移交，不顺手改。

方法与技术栈无关：结论落在元素角色、布局行为和度量数值上，不绑定某个框架的类名或组件实现。

## 设计通用性要求

1. **规范优先级**：目标产品已有设计系统与令牌 → 目标平台原生规范 → 行业通用规范 → 本技能规则。冲突时按此顺序取舍，并把冲突显式写进结论，不静默采用某一方。
2. **平台显式声明**：桌面、Web、移动端的硬性指标不同（命中区域、窗口行为、快捷键、手势）。每条结论标明适用平台，跨端套用前先确认前提成立。把网页做法直接搬进桌面应用，是最常见的系统性缺陷来源，详见「桌面客户端规范」。
3. **阈值给数值**：能写成数值的判定（对比度、目标尺寸、行宽、间距、时长）一律写数值，避免"更明显一些"这类不可验收的表述。
4. **规则与技术栈解耦**：描述问题用"该行内的文本容器"而不是"某个类名"，让结论能迁移到任意组件库。
5. **术语中性**：不引入特定产品的专有名词充当通用概念；引用外部规范时写明来源与条款编号，便于复核。
6. **先读本地规范**：目标仓库若存在设计系统、令牌文件或设计决策记录（常见于 `design-system/`、`DESIGN.md`、`docs/decisions/`、令牌 JSON），先读并以其为第一约束；不存在时按行业规范兜底，不因缺少文档停止工作。

### 无障碍与包容性（强制基线）

依据：WCAG 2.2 AA 级、ARIA Authoring Practices、EN 301 549、GB/T 37668-2019《信息技术 互联网内容无障碍可访问性技术要求与测试方法》、工信部《移动互联网应用（APP）适老化通用设计规范》。

| 约束 | 阈值 | 条款参考 |
| --- | --- | --- |
| 正文文本对比度 | ≥ 4.5:1 | WCAG 1.4.3 |
| 大号文本对比度（≥18pt，或 ≥14pt 粗体） | ≥ 3:1 | WCAG 1.4.3 |
| 非文本对比度（图标、边框、图形、状态点） | ≥ 3:1 | WCAG 1.4.11 |
| 目标尺寸 | ≥ 24×24 CSS px；推荐 ≥ 44×44 | WCAG 2.5.8 |
| 键盘可达 | 全部功能可键盘完成，焦点可见且不被遮挡 | WCAG 2.4.7 / 2.4.11 |
| 焦点指示 | 与相邻颜色对比 ≥ 3:1；2 CSS px 厚周长与未聚焦对比 ≥ 3:1 属 AAA 增强项 | WCAG 1.4.11 / 2.4.13 |
| 文本放大 | 200% 不丢失内容、不需横向滚动 | WCAG 1.4.4 |
| 重排 | 320 CSS px 宽或 400% 缩放不出现二维滚动 | WCAG 1.4.10 |
| 文本间距 | 行高 1.5、段距 2em、字距 0.12em、词距 0.16em 时内容不截断 | WCAG 1.4.12 |
| 颜色之外的信息冗余 | 状态不能只用颜色区分，需叠加文字或形状 | WCAG 1.4.1 |
| 错误提示 | 指出出错项并说明如何修正，不用笼统提示 | WCAG 3.3.1 / 3.3.3 |
| 替代文本 | 承载信息的图标与图片有等价文本，装饰性内容被忽略 | WCAG 1.1.1 |
| 指针操作的替代路径 | 拖动、多指手势有单击或键盘替代 | WCAG 2.5.1 / 2.5.7 |
| 适老化 | 字号与对比可放大、点击区域足够、不设置强干扰的强制操作 | 适老化规范 |

模态实现要点（ARIA Authoring Practices）：打开时焦点进入对话框并限制在内部，Esc 可关闭，关闭后焦点回到触发元素；页签、下拉框、组合框的键盘语义与角色对齐。

### 平台设计规范

- Apple HIG：触控目标 ≥ 44×44 pt；导航与工具栏层级；iOS 与 macOS 的差异不可直接互套。macOS 应用的菜单栏、窗口控件位置、⌘ 快捷键沿用系统约定。
- Microsoft Fluent 2 / Windows 11：桌面窗口、命令栏与信息密度约定；指针目标建议 ≥ 32×32 px，触控目标更大。WinUI / WPF / UWP 应用沿用系统控件样式，不自绘原生控件替代品。
- Google Material Design 3：触控目标 48×48 dp；动效时长与状态层规范。
- GNOME HIG / KDE HIG：Linux 桌面的菜单栏、工具栏与键盘约定；跨平台应用在两个桌面环境下都要能跑通快捷键。
- 桌面外壳技术栈（Electron、Tauri、WebView2、CEF、Avalonia、JavaFX、Uno）：外壳能力决定可用的系统集成项，先确认目标外壳提供了哪些原生接口，再决定界面能承诺什么。
- 企业级 Web 组件规范（如常见中后台设计体系）：表单、表格、密集数据布局的参考，用于对齐业界惯例，不作强制。

### 设计令牌与视觉体系

- 令牌分层：基础值（颜色、字号、间距）→ 语义（主文本、次要文本、危险、边框）→ 组件级。参考 W3C Design Tokens 社区组格式。
- 间距：4pt 基线、8pt 栅格；常用阶梯 4 / 8 / 12 / 16 / 24 / 32。
- 字号阶梯：模块化比例 1.125 / 1.2 / 1.25；桌面正文 14–16px，元信息不低于 11–12px。
- 行高：正文 1.5，标题 1.2–1.35。
- 行宽：45–75 字符，理想约 66。
- 圆角与阴影：同一层级只用一档；层级靠一两个变量区分，不逐页自定义。
- 颜色：语义色板而非字面色值；深浅色主题共用语义层，不各写一套。

### 内容与文案

- 可用性启发式（Nielsen Norman Group 十条）：系统状态可见、贴近用户语言、用户可控、一致性与标准、防错、识别优于回忆、灵活高效、简洁美观、帮助识别与修复错误、提供帮助与文档。
- 写作规范（Microsoft Writing Style Guide、Apple Style Guide）：动词开头、短句、面向结果、避免营销化形容词。
- 错误文案三段式：发生了什么、影响什么、下一步怎么做。不指责用户，不暴露内部错误码，但保留可复制的诊断标识。
- 界面文案是标签不是说明书：删掉后不影响决策的信息就删掉；需要解释时用一句短提示或帮助入口承载。

### 交互与状态

- 响应时间阈值：< 100ms 视为瞬时；100ms–1s 必须给即时反馈；> 1s 需要进度或可取消（Nielsen 0.1 / 1 / 10 秒原则）。
- 动效时长：小元素 100–200ms，中等 200–300ms，大范围 300–500ms；必须尊重 `prefers-reduced-motion`。
- 加载表达：结构已知用骨架屏，时长未知用加载指示；避免长时间无变化。
- 状态完备：按下面的「内容状态完备性」逐项交代，禁用态另按控件自身设计。
- 刷新策略：同一数据源只保留一个刷新入口；引入轮询前必须给出周期、触发条件与开销评估，默认优先事件驱动。
- 操作可逆：破坏性操作需二次确认或可撤销；耗时操作可取消。

### 内容状态完备性

每个数据区域都要交代六种状态。缺哪个，就在报告里点名哪个，不要用「状态已覆盖」一句带过。

| 状态 | 必须说明的三件事 | 常见缺陷 |
| --- | --- | --- |
| 加载中 | 结构是否稳定、是否显示进度、能否取消 | 整页转圈导致布局跳动；长任务只有旋转图标没有文案 |
| 空 | 区分「还没有数据」与「筛选后为空」、给出首个可执行动作 | 两种空态共用同一句「暂无数据」，用户不知道下一步 |
| 错误 | 具体失败原因、影响范围、恢复路径 | 只显示「操作失败」，不说明重试会不会重复扣费 |
| 部分可用 | 哪些数据已就绪、哪些缺失、缺失是否有替代 | 一条子请求失败就让整页变成错误态 |
| 成功 | 是否完成、下一步做什么、能否撤销 | 只闪一个 toast，关键结果没有留在页面上 |
| 无权限 | 边界是什么、如何申请、申请后回到哪里 | 直接隐藏功能入口，用户不知道功能存在 |

某一状态确实不适用时，要写明理由（例如只读系统没有「成功提交」）。测不到的环境属于未验证状态，不等于不适用。

## 与专项技能的分工

本规范给判定与审查口径，具体实现落到专项技能：

| 需要做的事 | 用哪个 |
| --- | --- |
| 语义角色、键盘路径、焦点管理、读屏标签的实现配方与逐条审计报告 | 界面无障碍 |
| 同心圆角、光学对齐、阴影分层、命中区、动效时长的具体取值 | 界面工艺细节 |
| 从零生成设计系统、选风格配色字体、维护令牌文件 | 界面设计助手 |

三者与本案的关系是「审查者与实现者」：本案判定哪里不合格，专项技能负责怎么改。同一轮工作里不要用实现时的心智自证通过，审查要另起一遍。

桌面与 WebView 应用的键盘实现细节按「界面无障碍」做，命中区与控件尺寸的具体取值按「界面工艺细节」做；但**窗口语义、快捷键集合、外壳接管与系统集成**由本案定义，专项技能不重复给规则，避免两处口径漂移。

## 国际化与本地化

- 预留文本膨胀 30%–50%（拉丁语系相对英文），中文与西文混排留出标点挤压空间。
- 文字不放进图片；日期、数字、货币、单位按语言环境格式化。
- 支持从右到左语言时使用逻辑属性（`margin-inline`、`padding-block`），不使用物理方向。
- 快捷键在 macOS 上把 Ctrl 换成 ⌘，并避开与系统快捷键冲突的组合。

## 桌面客户端规范

网页与桌面的差别不是视觉风格，是用户的物理预期不同：桌面用户带着操作系统十几年的肌肉记忆来，违背它就会被判定为"这不是个正经应用"。三条前提决定了下面所有条目：

1. **键盘是一等公民**。网页可以把键盘当增强，桌面上 Tab 走不通、快捷键不响应、焦点环不可见，就等于功能缺失。
2. **窗口是容器，不是视口**。网页假定一个固定视口；桌面应用有大小、位置、生命周期、多个实例、多个显示器。
3. **外壳也是界面的一部分**。WebView 混合应用里，标题栏、菜单、托盘、系统对话框都参与体验判定，不能只审页面内部。详见「WebView 混合应用」。

### 桌面阈值基线

| 约束 | 桌面取值 | 与 Web 的差异 |
| --- | --- | --- |
| 指针目标 | ≥ 32×32 px（Fluent 2 建议值） | 桌面指针精确，可比 Web 的 44/48 更小；触屏设备仍按 44 |
| 正文字号 | 14–16 px | 一致；但桌面行宽更宽，可承载更长行 |
| 元信息字号 | ≥ 11 px，常用 12 px | 桌面信息密度更高，允许更小 |
| 控件高度 | 紧凑 28–32 px，常规 32–40 px | 明显小于 Web 的 40–48 |
| Tab 焦点环 | 键盘进入必显示，对比 ≥ 3:1 | 鼠标点击时可隐藏，键盘进入时必须出现 |
| 滚动条 | 常驻占位宽度 | WebView 在部分平台默认覆盖式，需显式改为占位式 |

### 键盘语义

- **Tab 必须遍历全部可操作元素**，顺序符合视觉顺序；不允许出现"鼠标能点、Tab 跳不过去"的控件。
- **焦点环按输入方式区分**：用 `:focus-visible` 或等价手段，键盘进入必须显示，鼠标点击可隐藏。整体移除 outline 又不给替代焦点态，是桌面端最高频的无障碍缺陷。
- **访问键**：Windows / Linux 上高频动作给 Alt + 字母，菜单项给助记符；同一窗口内助记符不重复。macOS 不用访问键，用 ⌘ 组合。
- **单键操作要克制**：Delete 删除选中项前必须有确认或撤销；空格在列表里切换选中而非滚动。

### 快捷键基线

下列按键在桌面应用里属于**预期存在**。不实现某项时必须是有意识的决定，并写进验收清单，而不是遗漏。

| 快捷键 | 预期行为 |
| --- | --- |
| Ctrl + S | 保存当前文档；不可用时有明确的"无需保存"反馈 |
| Ctrl + Shift + S | 另存为 |
| Ctrl + Z / Ctrl + Shift + Z（或 Ctrl + Y） | 撤销 / 重做，范围覆盖最近一次编辑 |
| Ctrl + C / X / V | 复制 / 剪切 / 粘贴，遵循当前焦点的元素语义 |
| Ctrl + A | 全选当前上下文，不是全选整页 |
| Ctrl + F | 应用内搜索，**不得是浏览器查找框** |
| Ctrl + W | 关当前文档或标签；不直接退出进程 |
| Ctrl + N / Ctrl + O | 新建 / 打开 |
| Esc | 关闭最上层浮层（对话框、下拉、命令面板），不退出应用 |
| Delete | 删除选中项，弹确认或提供撤销 |
| F5 / Ctrl + R | 刷新数据；若要重载界面，必须先拦截未保存内容 |
| Ctrl + , | 打开设置（macOS 用 ⌘ ,） |
| F1 | 帮助或文档入口 |

快捷键冲突的处理顺序：系统级快捷键（如 Ctrl + Alt + Del）不可占用 → 应用级快捷键 → 控件级。同一组合不在两个层级同时响应。

### 窗口语义

每个桌面应用都必须能回答下面这张清单。任一项说不出答案，就是设计缺口，不是实现细节。

| 问题 | 必须给出的答案 |
| --- | --- |
| 默认尺寸 | 给出最佳工作尺寸，不是全屏最大值 |
| 最小尺寸 | 低于该尺寸时的降级行为（折叠侧栏、换行工具栏、出现横向滚动） |
| 位置记忆 | 记住尺寸与位置；副显示器断开后不落在可视区外 |
| 关闭行为 | 隐藏到托盘 / 退出进程 / 只关当前文档，三选一且全应用一致 |
| 未保存拦截 | 关闭前检查脏状态，给出保存 / 丢弃 / 取消三选项 |
| 实例模型 | 单实例（再次启动聚焦已有窗口）还是多实例 |
| 窗口层级 | 主窗口、子窗口、模态对话框的作用域（只挡父窗口还是整个应用） |
| 全屏与贴边 | 最大化、全屏、分屏贴边的行为 |
| 标题栏 | 用原生还是自绘。自绘必须同时恢复：拖动、双击最大化、右键系统菜单、边缘缩放 |

高 DPI：一律使用逻辑像素；位图图标提供 16 / 20 / 24 / 32 多档位，或改用矢量；不得出现模糊、错位或半像素描边。

### 滚动模型

- **页面本身不滚动**。桌面是多区域独立滚动：侧栏自己滚、主工作区自己滚、表格内部自己滚。整页一个长文档只在阅读类界面成立。
- 滚动条用**占位式**而非覆盖式，避免内容宽度随滚动条出现而跳动。
- 长列表超过 200 行时使用虚拟滚动；表格记录列宽、列序与排序状态。
- 嵌套滚动区不超过两层，否则滚轮指向不明确。

### 状态归属

桌面应用要把状态分成两层，混在一起会导致未保存提示失效：

- **应用级**：窗口几何、偏好设置、最近打开列表、登录态。随进程存活，落盘保存。
- **文档级**：当前编辑内容、撤销栈、光标位置、滚动位置。随文档存活，关文档即失效。

崩溃恢复至少覆盖文档级状态；应用级状态损坏时可安全重置。

### 信息密度

- 桌面用户坐着、屏幕大、任务时间长，能承受更高信息密度。网页的"大标题 + 大留白 + 卡片流"搬进桌面等于浪费空间且低效。
- 工具栏、命令栏、状态栏是桌面的固有结构，不要退化成网页式的顶部导航 + 内容区。
- 表格默认显示更多列；元信息用小字号就近排布，不单独占一行。
- 列表行高紧凑（28–36 px），选中态与悬停态必须有区分。

### 系统集成

| 能力 | 要求 |
| --- | --- |
| 应用菜单 | macOS 必须进全局菜单栏，菜单项与快捷键一一对应；Windows / Linux 用窗口内菜单栏或命令栏 |
| 托盘 / 菜单栏图标 | 提供显示窗口、退出两项；有后台任务时图标状态可区分 |
| 任务栏 / 程序坞 | 长任务显示进度，未读数显示徽标 |
| 系统通知 | 可关闭；点击通知回到对应上下文 |
| 文件拖放 | 支持拖入文件到窗口与拖出到系统文件管理器；拖放有可视落点提示 |
| 系统文件选择器 | 一律调用原生对话框，不自绘 |
| 外部链接 | 用系统默认浏览器打开，不在应用内导航 |
| 深链接 | 从外部唤起时定位到具体资源，不落到首页 |
| 自动更新 | 给下载进度、重启时机与延后选项；不在用户输入过程中强制重启 |

## WebView 混合应用

Electron、Tauri、WebView2、CEF 一类应用的核心风险是**外壳被当成透明的**：页面按网页习惯写，结果是外壳的浏览器语义直接暴露给用户。判定口径是：用户看到的行为必须由应用定义，不能由浏览器默认值定义。

### 必须接管的浏览器默认行为

下表每一项都是 WebView 里"默认就会发生、但用户不预期"的行为。审查时逐条实按一次，确认行为是经过设计的。

| 触发 | 浏览器默认 | 桌面应用应改为 |
| --- | --- | --- |
| Ctrl + W | 关闭窗口或整个应用 | 关闭当前文档 / 标签，无标签时不响应 |
| Ctrl + R / F5 | 重载页面，未保存内容丢失 | 刷新数据；有脏状态时先拦截 |
| Ctrl + F | 弹出浏览器查找框 | 应用内搜索，或显式禁用 |
| Ctrl + P | 打印对话框 | 按应用需要接管或禁用 |
| Ctrl + +/- / 0 | 整页缩放 | 按产品需要接管；不得让布局崩坏 |
| 右键 | 浏览器上下文菜单（后退、重新加载、检查元素） | 应用自己的上下文菜单，或按位置禁用 |
| 拖入文件 | 页面导航到 `file://` 路径 | `preventDefault` 后作为应用内文件接收 |
| 拖出元素 | 无行为或拖出链接 | 按需支持拖出到系统 |
| 中键点击链接 | 尝试新开窗口 | 禁用，或改为应用内打开 |
| F12 / Ctrl+Shift+I | 开发者工具 | 生产构建中禁用 |
| Tab 键 | 只在表单控件间移动 | 按桌面 Tab 顺序遍历全部可操作元素 |
| 空格 / 方向键 | 滚动页面 | 页面不滚动，由内部滚动区接管 |
| Esc | 无行为 | 关闭最上层浮层 |
| 后退导航 | Alt + ← 或鼠标侧键退出当前页面，可能直接离开应用 | 拦截浏览历史；导航只由应用自身路由驱动 |

**关键点**：`window.confirm` / `alert` / `prompt` 一律不用，改为应用内对话框——原生浏览器弹窗在不同平台上样式不一，且会阻塞渲染进程。

### 外壳与页面的一致性

页面内容与外壳经常割裂，判定方法是把窗口切走、最小化、跨显示器拖动，观察外壳与内容的响应是否同源。

- **拖拽区域**：自绘标题栏时，可拖动区必须显式标记（`-webkit-app-region: drag` 或等价），其中的按钮、输入框必须标回 `no-drag`，否则点击失效。
- **主题同步**：外壳菜单栏、原生对话框、标题栏跟随应用的深浅色主题；系统切换主题时即时响应，不要求重启。
- **焦点边界**：从页面 Tab 到外壳控件再 Tab 回页面，顺序不断裂；外壳元素同样参与焦点可见性。
- **快捷键作用域**：快捷键在输入框内是否生效要显式定义。文本编辑型输入框内，单键快捷键（如删除、字母键）必须让位；组合键（Ctrl + S）仍应生效。
- **加载态**：WebView 首屏白屏超过 300 ms 必须给启动画面或骨架，不能出现无提示的空白窗口。
- **错误边界**：渲染进程崩溃时给出可读的提示与重启入口，不留下一个空白窗口。

### WebView 侧的尺寸与命中区

浏览器与桌面外壳对 CSS 像素的处理不同，以下取值需要在外壳环境中重新确认，不能直接沿用网页设定：

- `min-width` / `min-height` 要按窗口最小尺寸校验，而不是按浏览器视口校验。
- 命中区按桌面阈值（≥ 32×32 px）核对，若产品同时支持触屏则取两者较大值。
- `100vh` 在部分外壳中不等于窗口高度（存在标题栏与状态栏占位），改用容器高度或外壳注入的尺寸变量。
- 滚动条宽度因外壳而异，覆盖式与占位式必须显式设置。
- 系统缩放在 125% / 150% / 200% 下逐一核对，避免半像素描边与图标模糊。

### WebView 独有安全与信任边界

这部分是界面问题而非纯安全问题，因为它直接决定用户看到什么：

- 外部链接一律走系统浏览器，不在应用内导航。
- 内嵌第三方页面必须收在明确的容器内，并让用户能看出"这是外部内容"。
- 原生与页面之间的双向通道要有明确的失败表现：调用超时时给用户可读的提示，不是静默无响应。
- 权限请求（文件、摄像头、通知）由应用统一弹窗说明用途，不直接透传 WebView 默认弹窗。

## 去 AI 味与主流方案对齐

"AI 味"指界面看起来像模板生成：字数多而信息少，情绪词多而具体信息少，装饰多于功能。它同时出现在文案和视觉两侧，都属于可判定的问题。

### 文案约束

出现即改写，不论上下文：

- 空泛动词与名词：赋能、助力、打造、一站式、无缝、极致、全链路、生态、闭环、全新升级、重磅、深度解析。
- 营销与拟人句式：让……更……、开启……之旅、与……一起……、从这里开始、只需一步。
- AI 自述语：作为 AI……、让我帮你……、我正在为你……。这类过程自述不应出现在界面文案里。
- 情绪化标点：正文用 emoji 充当图标或装饰；状态提示以感叹号结尾。
- 三段式排比：界面里出现三行以上并列修辞，通常是为了撑版面而非传递信息。
- 过度解释：把"此操作将会……"这类铺垫改成动词短语或一句结论。

正向规则：

- 用名词短标签或动词短语，只说一句话能说完的信息。
- 直接给结论与后果，不铺垫背景、不做自我介绍。
- 一个概念全产品只用同一个词，不混用"安装 / 添加 / 获取"。
- 数量与单位写具体值，不写"大量""多种""高效"。
- 中文标点用全角，中英文混排空格按团队规范统一。
- 空状态、错误提示、按钮分别只承担一件事：说明现状、说明原因与下一步、说明动作。

检查方法：

1. 删掉句中所有形容词与副词，若信息没有减少，原句需要重写。
2. 把文案念一遍；像宣传语或像客服话术的，改写。
3. 让不熟悉产品的人只读标签，判断能否猜出功能。

### 视觉与交互约束

- 配色不默认使用紫蓝渐变、霓虹发光、玻璃拟态制造"科技感"；主色来自品牌或产品既有令牌。
- 同一层级只用一档圆角与阴影，不用超圆角叠加多层阴影制造精致感。
- 不用星星、闪光这类泛化符号代表"AI 能力"；图标表意优先于装饰。
- 空态与首屏不用"大图标 + 居中大标题 + 营销副标题 + 三张卡片"的模板式排版，直接说明当前状态与第一个可执行动作。
- 动效只服务于状态变化与因果关系，不为每个元素加入场动画。
- 装饰性渐变与背景图不得降低文本对比度，也不得干扰文字识别。
- 插画不是必需品；需要时保证语义明确，不为填满空间放装饰图。

### 结合主流方案

- 参照对象按场景选：对话类看 ChatGPT / Claude，开发工具看 VS Code / GitHub，项目管理看 Linear / Notion，系统设置看 macOS 系统设置与 Windows 设置，团队协作看 Slack。
- 方法：先找到主流方案在同一位置的等同界面，比较三件事——用什么词、放在哪、有多少元素。有差异必须有产品理由，没有理由就回到主流做法。
- 只借鉴结论稳定的共识（设置归到账号菜单、保存后即时反馈、错误就近提示），不照抄依赖产品前提的设计。
- 主流做法与本产品设计系统冲突时，以本产品设计系统为准，并把冲突写进审查报告。

### 审查报告自身也去 AI 味

- 结论先行，不写"综上所述"式的收束段。
- 不堆排比，不写情绪化评价，只写现象、影响与改法。
- 不复述用户原话，不重复已知结论。

## 七个审查方向

同一现象只归一个主方向，避免重复计数。

### 1. 信息架构与导航

入口表达用户任务，不表达内部技术模块。

- 一级导航按"用户要完成什么"分组，组名用业务语言；分类标签下的条目应能被一句话概括共同点。
- 一个功能只保留一个主入口，其他位置作为上下文快捷方式，不重复出现在两个平行入口。
- 高频动作靠近主工作区，低频配置下沉到设置；设置类入口归到账号或身份区域，符合主流工具心智。
- 状态类内容（任务中心、待处理数量）做成常驻状态入口，不占一级菜单位。
- 图标表意，避免用通用符号表达专有概念；导航层级深度不超过两级。

判定方法：把每个菜单项改写成"用户要做的动作"，写不出动作或与相邻项语义重叠，则该条目位置有问题。

### 2. 布局与响应式容纳性

最高频、最容易被忽略的一类问题，优先级最高。

- 横向流式行内出现不可控长文本（URL、文件路径、ID、错误信息、模型名、包名）时，文本容器必须可收缩，并配合断词或省略号。
- 文本容器宽度不超过父容器；`nowrap` 与长文本的组合是溢出高发点，逐个确认。
- 列表或卡片行内的主操作（安装、卸载、启动、授权）不得被标题或描述挤出可视区：文本列负责收缩，操作列不收缩。
- 错误提示、校验信息、多行说明允许换行并撑满可用宽度。
- 概览与元信息区用自适应列数，替代按断点写死的固定列。
- 窄窗口下工具栏与页头换行而不是顶出容器；主从布局折叠后不同时渲染两个面板。
- 容器查询或等价手段优先于全局断点，让组件在任意容器宽度下成立。

判定方法：把窗口压到最小尺寸与 320px 等极端宽度，检查是否出现横向滚动、文字溢出父容器、操作按钮被裁切。

### 3. 视觉层次与间距节奏

- 只用令牌阶梯（4 / 8 / 12 / 16 / 24 / 32）；同类元素间距一致。
- 页面顶部、区域顶部、卡片内边距分别对齐，同一层级不允许两套边距。
- 同类卡片、同类列表项的描述与数值边距完全一致，形状差异只来自内容。
- 列对齐优先于等距：成组内容共用同一左基线；数值列右对齐，文本列左对齐。
- 字号、行高、控件高度、圆角使用语义令牌，不写裸数值。
- 层次靠字重、颜色与间距建立，避免用多重边框和阴影堆叠。
- 不使用模板感的装饰手法（紫蓝渐变、玻璃拟态、泛化星光图标），配色取自产品令牌，详见「去 AI 味与主流方案对齐」。

判定方法：并排比对同类元素的实际内边距与字号取值，而不是凭截图观感判断。

### 4. 内容与文案

- 字段名尽量控制在六个汉字以内；同类字段在所有页面同名。
- 删除解释性长句，删除不影响决策的信息。
- 同一区域使用统一句式与句长，不混用陈述句、命令句与疑问句。
- 状态文案直接给结论与下一步，不堆修饰词。
- 文案长度按本地化膨胀上限校验，预留空间。
- 不出现空泛动词、营销句式与 AI 自述语；同一概念全产品用同一个词。详见「去 AI 味与主流方案对齐」。

判定方法：逐条读文案，若删掉后用户不损失决策信息，则删掉。

### 5. 交互与状态反馈

- 每个可点击控件都有明确的进行中、成功、失败状态；长时任务有持续可见的运行态反馈。
- 响应超过 1s 的操作给出进度或可取消，不出现无变化的等待。
- 同一数据源只保留一个刷新入口；存在自动刷新时手动刷新通常冗余。
- 六种内容状态逐个核对，缺项按上文「内容状态完备性」记为问题；不可用态说明原因与恢复方式。
- 破坏性操作可撤销或二次确认。

判定方法：统计每个轮询或定时刷新在一个周期内的请求量，判断能否被事件驱动替代。

### 6. 无障碍与包容性

- 按上文阈值核对对比度、目标尺寸、文本间距与放大行为。
- 键盘走一遍主流程：Tab 顺序符合视觉顺序，焦点可见，对话框可 Esc 关闭且焦点回到触发处。
- 状态与错误不只靠颜色传达。
- 语义化结构：标题层级连续，表单控件有关联标签，表格有表头，图标按钮有可读名称。
- 深浅色主题各自核对对比度，不假设深色主题自动通过。

判定方法：只用键盘完成一次核心任务；把主题切到另一套配色重新核对对比度。

### 7. 一致性与规范对齐

- 同类操作在所有页面使用同一文案、同一图标、同一位置。
- 参考同类主流工具已验证的交互位置约定（账号与设置的关系、状态入口位置、主从布局顺序），没有充分理由不另创新模式。
- 操作聚合要克制：单一动作直接外显；只有同类并列的次要操作才收进更多菜单。
- 主按钮、次要按钮、危险操作的视觉层级保持一致。
- 同一组件在不同页面的尺寸、圆角、间距取自同一令牌。
- 文案与交互与主流同类工具的同位置保持一致；例外必须有产品理由。详见「去 AI 味与主流方案对齐」。

判定方法：列出该动作在其他页面的呈现方式，不一致时统一到使用频次最高的一种。

## 桌面与 WebView 专项核对

七个审查方向对桌面应用同样适用，但下面这些现象只在桌面出现，需要单独走一遍。审查面向桌面客户端时，这一节不作为可选补充，而是必查项。

### A. 外壳接管核对（仅 WebView 混合应用）

按「必须接管的浏览器默认行为」表逐条实按。每条记录三件事：按下什么、现在发生什么、应该是什么。出现"浏览器原生行为直接暴露"的，一律按最高优先级记为问题——它同时违反一致性、平台适配与品牌可信度。

重点复验四条最容易漏的：Ctrl + W、Ctrl + R、右键菜单、Alt + ← 后退。

### B. 键盘完整性核对

- 只用键盘完成一次核心任务，全程不碰鼠标。
- Tab 顺序记录一遍，与视觉顺序比对。
- 逐个确认快捷键表里承诺的组合真的生效，以及在输入框内外的作用域差异。
- 焦点环在深色与浅色主题下各确认一次可见性。
- 悬停态与焦点态在视觉上可区分（悬停不显示焦点环，但焦点必须显示）。

### C. 窗口与外壳核对

- 拖到最小尺寸：是否出现横向滚动、按钮裁切、文字溢出。
- 拉到最大与全屏：内容是否被拉伸变形，表格是否出现过度留白。
- 跨显示器拖动，以及断开副显示器后重新启动：窗口是否仍可见。
- 缩放系统到 125% / 150% / 200%：图标、描边、文字基线是否仍清晰。
- 自绘标题栏：拖动、双击最大化、右键系统菜单、边缘缩放四项是否都恢复。

### D. 生命周期核对

- 有未保存内容时关闭窗口：是否拦截，三个选项是否都可用。
- 后台运行中从托盘唤起：是否回到原状态而不是重启。
- 深链接从外部唤起：是否定位到具体资源。
- 长任务进行中切走再切回：进度是否连续，不出现重置或重复触发。

判定方法：桌面审查的"真机复验"必须在目标外壳中完成，不能用浏览器模拟窗口尺寸代替。浏览器里通过的键盘与窗口行为，在外壳里可能完全不成立。

## 产出物

审查完成后输出结构化报告：

1. **问题清单**：编号、现象、证据（截图或元素选择器）、方向归类、根因、修复方案、验收标准、优先级。
2. **规范依据**：每条结论给出所依据的规范与条款，或说明来自目标产品自有设计系统。
3. **方向归类汇总**：说明问题集中在哪几个方向，指出系统性问题而非孤立瑕疵。
4. **修复方案**：精确到文件与选择器，写明改动内容与影响范围。
5. **验收标准**：可复验的判定条件，例如"最小窗口宽度下全页无横向滚动""同类卡片内边距为 16px""正文对比度 ≥ 4.5:1"。

审查桌面客户端时，问题清单另加两列：**适用平台**（Windows / macOS / Linux / 全平台）与**外壳层或页面层**。跨平台差异项拆成独立条目，不合并成一条"桌面端有问题"。

实施后补充一条结论：改了什么、验证方式、遗留项。

## 落地形态

样式问题通常是散落在几十个选择器里的同一个根因。优先把修复收敛成集中、可读、可长期维护的约束，而不是逐页打补丁。

**集中式约束块**：在样式表末尾维护一段编号的界面约束区块，每条一行注释加一组选择器。编号让规则可被引用与复查，注释记录这条规则为什么存在（真实症状比抽象原则更能防止被误删）。适合收纳的内容：

- 溢出安全网：长文本元素的断词与省略规则。
- 行内徽标保持内联排布，不被列表的通用容器规则拆成多行。
- 弹性与网格子项默认可收缩，长内容不挤出兄弟节点。
- 工具栏、页头在窄窗口换行而不是顶出容器。
- 概览与元信息网格使用自适应列数。
- 控件高度、圆角、页签高度统一到令牌。
- 列表文字层级统一，元信息不抢视线。
- 滚动区域内滚动条不压住内容。
- 窄窗口下主从布局折叠、操作按钮占满整行。
- 尊重系统动效偏好，避免全局动画。
- 桌面：页面容器不参与整页滚动，滚动只发生在内容区。
- 桌面：滚动条使用占位式，避免内容宽度跳动。
- 桌面：外壳可拖动区与不可拖动区显式标记，避免自绘标题栏点不动。

集中式约束的价值在于：一次修复覆盖同类页面，新增页面自动继承。

**令牌化**：把字号、行高、间距、圆角、控件高度、语义色写入令牌，界面只引用语义层；改版时改一处。

**客观断言**：对可度量的约束补校验脚本（页面结构、元素数量、图标来源版本、令牌引用），纳入项目检查命令，防止后续回退。

## 验证要求

1. 真机复验：在真实运行的界面上确认修改生效，不接受只看代码。
2. 极端条件复验：最小窗口宽度、320px 宽度、最长文本、空数据、错误数据、放大 200% 各走一遍。
3. 键盘与主题复验：只用键盘完成核心任务，深浅色主题各核对一次对比度。
4. 回归检查：确认改动没有影响同页其他区域，也没有把问题从一处挪到另一处。
5. 客观断言：能用脚本或度量确认的（滚动宽度、边框盒尺寸、间距与对比度数值）尽量给出断言，不留纯主观结论。

### 渲染验收门

只读源码不能作为通过依据。交付前在目标视口下实际渲染并留下证据：

- 记录视口清单（例如 `390x844`、`1440x900`），每个目标视口至少一张截图或一段浏览器测试产物，产物留在工作区内。
- 桌面客户端记录的是**窗口尺寸**而非视口尺寸（例如 `1280x800` 默认、最小尺寸、最大化），并在目标外壳中截图。
- 每个适用状态各演练一次，包含部分可用；不适用要写理由。
- 每份产物写明它证明了什么，例如「窄视口下工具栏换行，无横向滚动」「外壳中按 Ctrl + W 只关文档不退出应用」。
- 截图与录屏不能证明的部分（读屏播报、焦点顺序、快捷键是否被外壳吃掉）另做键盘与读屏走查，并把结果写进结论。

桌面与 WebView 应用另加一条硬性要求：**在浏览器里调整窗口宽度不等于桌面验收**。同一份页面在外壳中的窗口最小尺寸、快捷键拦截、滚动条样式、系统缩放下都可能不同，必须在目标外壳里复验一次，否则记为「未进行桌面验证」。

无法渲染时，在结论里明确写「未进行渲染验证」并列出待人工确认项，不要用「应该没问题」替代。
