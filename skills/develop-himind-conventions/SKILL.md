# 扩展开发规范

插件、技能、工作流三类扩展共用的判断规则。类型专属的字段清单、脚手架和流程在对应的开发技能里；长度阈值由 `tooling/metaguide` 定义、脚手架和校验强制执行，本规范不重抄一遍。

## 工作边界

1. 本规范只给判断口径：什么时候该做哪类扩展、名字和说明怎么写、依赖和分发怎么定。
2. 确定性操作在插件开发助手、技能开发助手、工作流开发助手里执行；本规范不替代它们的校验和打包。
3. 规则冲突时按此顺序取舍：目标产品已有约定 → 本规范 → 个人偏好。冲突要在交付说明里写出来，不静默选一边。
4. 长度上限以校验器报错为准，建议值只作提示。拿不准就调用 `extension.environment.preflight`，它返回同一份规则与字段约束。

## 一、先选对类型

| 类型 | 承载什么 | 不该放什么 |
| --- | --- | --- |
| 插件 | 确定性文件处理、进程调用、专业格式解析、设备与网络操作 | 对话式操作知识、流程编排 |
| 技能 | 触发条件、操作知识、Capability 编排、降级策略 | 确定性解析、构建、设备操作 |
| 工作流 | 跨步骤执行、审批、Artifact、交付状态、Loop | 插件实现、一次性操作知识 |

判定顺序：能写成确定性函数或命令的做插件；需要模型判断下一步的做技能；需要状态、审批和交付物的做工作流。同一个需求命中两类时，拆成插件提供能力、技能或工作流负责编排，不要在一类里硬塞另一类的职责。

## 二、命名

1. 显示名用名词短语，只说是什么，不写用途、不写动词短语、不叠领域限定。「微信小程序交付工具」合格，「微信小程序一键上传体验版」不合格。
2. 类型词要真实反映形态：插件提供确定性能力，用「工具」；技能承载操作知识，用「助手」或知识本身的名字（规范、摘要、反馈）；工作流用交付物名词（发布、日报、上传）。不要为了整齐给不相干的名称套同一种后缀。
3. 同一领域跨类型时用类型词区分。插件「软件分发工具」和技能「软件分发助手」是一对；两条都叫「软件分发」，用户在能力列表里无从判断该用哪个。
4. 不用承诺词和岗位词：智能、自动、一键、全能、极致、管家、专家、大师。
5. 用户可见文案用中文或通用缩写（Git、SVN、MCP、UNIHPer）；稳定 ID、目录名、frontmatter `name` 用小写 ASCII 连字符。
6. 显示名分散在 `skill.json.name`、`SKILL.md` 的 H1、`agents/openai.yaml` 的 `display_name`、`workflow.json.name`、`ui/workflow-view.json.title`。改名必须一次改全，否则「我的能力」和 Workflow 详情会同时显示两套名字。

## 三、说明与文案

1. 用途说明写「做什么 + 什么时候用」一句，不复述需求、不列功能清单、不写实现细节。
2. SKILL.md 的 frontmatter `description` 同时承载用途和触发场景，用「用户要求……时使用」收尾，让 AI 能凭这句话判断要不要加载。
3. 更新说明只写本次变化。功能没变就不改这条，不写累积功能清单。
4. 不用无法验收的词：一站式、全方位、赋能、助力、强大、领先、生态。也不用「第一次使用」「常见问题」这类填充语。
5. Capability 说明写清它做什么，用短句，不写它属于哪个实现或哪个版本。
6. 同一件事在一份扩展里只写一处。用户可见文案不重复出现在 `description`、正文和 `default_prompt` 里。

## 四、分类

从固定能力分类里选至少一个：`software-engineering`、`visual-design`、`video-post`、`3d-animation`、`content-production`、`audio-sound`、`data-automation`、`docs-knowledge`、`testing-quality`、`collaboration-delivery`、`system-device`。

分类描述能力领域，不写岗位、部门、权限或客户端名称。跨领域就多选，不新增自造分类。

## 五、依赖

1. 优先依赖稳定 Capability ID；只有必须绑定某个具体实现或资源时才写 `plugin_dependencies`，并给出真实的 `min_version`。
2. 只声明运行时真实依赖。`com.himind.extension-development-tools` 和四个创作技能是创作期工具，不是业务扩展的运行时依赖；写进业务扩展会迫使使用者安装整条创作工具链。
3. 缺失依赖要报 `blocked` 并给出补救步骤，不自动安装，也不为了通过测试伪造 Capability 或平台状态。
4. 工作流的依赖分 `skills`、`plugins`、`connectors`、`runtimes` 四类；凭据只通过 `credential_handles` 引用，不把真实值写进输入。

## 六、分发目标

`distribution_targets` 是硬约束，只有两个取值：

| 取值 | 含义 |
| --- | --- |
| `workbench` | 面向组织内审核与安装 |
| `github` | 对外公开：创建不可变 Release 并写入 `.himind/catalog.json` |

1. 声明是上限。Agent 侧只能在声明范围内收窄，不能扩权；越界选择会被拒绝并提示先改清单。
2. 缺字段仓库校验直接报错，不允许靠默认值兜底。`extensions.json` 里的 `default_distribution_targets` 只是脚手架默认值，不参与运行时判断。
3. 只声明 `workbench` 的扩展不创建 Release，也不写 Catalog——公开目录条目的定位信息就是 Release 资产。
4. 只对单个项目、单个客户或单个交付现场有效的功能，不放进公共目录。这类扩展放独立仓库，按项目分发，避免公共市场出现装不上的条目。

## 七、风险与权限

1. Capability 声明 `local`、`network_service` 或 `control_plane`，本地检查留在 `local`，组织发布与调度归 `control_plane`，不为两种形态复制两套实现。
2. 最小权限：只申请真实用到的权限，不申请「以后可能用」的权限。
3. 不读取或传递 Token、Cookie、私钥和 Agent credential；不直接改 Distribution 数据库；只在 `workspace_root` 内写文件；不接受任意 Shell、任意 URL 或越出工作区的路径。
4. 高风险写操作先出计划再执行，需要审批的步骤设 `approval_required`，并走 Agent 审批中心。

## 八、版本、兼容与提审

1. 语义版本，按影响面提升。已发布版本不得覆盖，也不得同版本替换；内容变了就提版本并更新 `release_notes`。
2. `min_agent_version` 只写真实依赖的下限，不写「当前版本」这类无意义的高位。
3. 声明支持哪些客户端时，通用技能用可移植的 `agent-skills`；只有明确依赖某个客户端的私有行为时才写具体客户端 ID。
4. 候选、确认、提审、签名、发布、撤回属于不同权限层。创作技能只负责产生不可变候选和发起提审，管理员权限不通过安装创作工具获得。

## 交付前自检

- 类型选对了：确定性能力在插件，操作知识在技能，状态与交付在工作流。
- 显示名是名词短语、类型词真实，且五个字段已经同步。
- 用途说明、触发说明和更新说明各写一处，没有重复描述和空词。
- 分类来自固定列表，没有自造分类。
- 依赖只有运行时真实依赖，没把创作工具链写成业务依赖。
- 分发目标与功能性质匹配：项目定制不进公共目录。
- 权限最小，凭据不落盘，写入不越出 `workspace_root`。
- 版本已提升，`release_notes` 只描述本次变化。
