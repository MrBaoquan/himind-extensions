# 长任务推进助手

把「已经聊清楚的事」变成「能自己做完的事」：先承接上下文形成**任务契约**，确认后**先接管客户端原生的目标/续跑机制**，再按可验证轮次持续实施，并在会话中断、上下文压缩或更换客户端后从状态文件恢复。

## 第一原则：优先用客户端原生目标，不要自己模拟续跑

**能力探测的顺序是「先找原生机制」，不是「先判文件能力」。** 大多数成熟客户端已经有会话级目标或自动续跑，技能的第一动作是把任务装进那个机制，而不是用状态文件假装它在跑。

已知的原生目标机制（客户端升级后以实际工具为准）：

| 客户端 | 原生机制 | 建立方式 |
|---|---|---|
| DSH | `create_goal` / `update_goal`，按轮自动 continuation | 确认后立即 `create_goal` |
| Codex | `create_goal` / `get_goal` / `update_goal`，`goals` 特性，`thread_goals` 表 | 确认后立即 `create_goal` |
| Claude Code | 会话内循环 / 目标类指令 | 确认后启动循环 |
| 其他 | 未知 | **主动探测一次**，不要假设没有 |

**强制动作：**

1. 立项阶段用一次只读探测确认有没有目标类工具，把结果写进 `state.capabilities.native_goal`。
2. **确认后必须先建立原生目标，再开始第一轮。** 没有建立就说「已自动推进」属于欺骗。
3. 原生目标存在期间，**每轮结束用 `update_goal` 维持 `active`**，不要让它被系统判成 idle 而中断续跑。
4. 只有验收全绿且人工项确认，才把原生目标置 `complete`；预算耗尽置 `budgetLimited`；同一阻塞连续 3 轮置 `blocked`。
5. 探测不到原生机制**才**降级到状态文件驱动的续跑块，并且要明确告诉用户「本客户端无自动续跑，需要你说继续」。

## 适用与边界

在以下情况使用：

- 用户与你多轮讨论后说「整理成任务」「就这么办」「开始做」。
- 任务跨多轮、跨会话，单次响应做不完。
- 用户要求「确认后你自己推进，别每步都问我」。
- 用户说「继续上次的长任务」。

不要用于：

- 一两步就能做完的小事——直接做。
- 纯讨论、方案还没收敛——继续讨论，不要立项。
- 路径完全固定、需要审批和交付物的流程——交给 Workflow。
- 真正长时间的外部执行（转码、抓取、构建）——交给后台作业或插件能力，本技能只负责调度与记录。

## 三个阶段

```text
收敛立项（只读） → 确认门 → 建立原生目标 → 自主执行（轮次推进） → 交付报告
                        ↑                                          │
                        └──────── 接续（新会话/换客户端）───────────┘
```

**立项轮禁止执行**：只读上下文、只产出契约，不修改业务文件，不运行会改变状态的命令。

## 状态目录

状态放在 `<工作区>/.himind/long-tasks/<task-id>/`。**原生目标是续跑引擎，状态文件是事实源**，两者都要维护：原生目标丢失或换客户端时，靠状态文件重建。

| 文件 | 用途 | 约束 |
|---|---|---|
| `task.md` | 目标、验收、范围与非目标、已决、未决假设、授权、预算 | ≤80 行，唯一事实源 |
| `state.json` | 阶段、轮次、下一步、阻塞、证据索引、能力探测 | ≤60 行 |
| `progress.md` | 每轮一条：目标/动作/证据/结果/下一步；每 5 轮压缩 | 只追加 |
| `decisions.md` | 执行期新决策及理由，防止下个会话重新讨论 | 只记非显然决策 |
| `handoff.md` | 给下一个会话或客户端的交接卡 | ≤30 行 |
| `evidence/` | 命令输出、测试报告、截图等原件 | 正文只引用路径与关键行 |

字段与模板见 `references/templates.md`。

## 阶段一：收敛立项

1. **判定入口**：只有用户表达「整理成任务 / 确认后执行 / 继续上次」才立项；纯讨论不立项。
2. **自己抽取，不让用户重述**。来源是当前对话、用户给的文件和仓库现状，抽取六类信息：
   - 目标结果：一句话，能判断是否达成。
   - 验收标准：逐条列出，尽量可机器验证。
   - 范围与非目标：尤其写清「不做」。
   - 已决事项与被否决方案及理由。
   - 未决项 → 默认假设：≤3 条，冲突再回报，不要停下来反复问。
   - 授权边界与预算。
3. **探测原生能力**：确认是否有目标类工具（`create_goal` / `update_goal` / 循环指令等），写入 `state.capabilities`。不确定就实际调用一次只读的目标查询，不要凭印象判断。
4. **验收写不出来时**：把第一轮定为「探索轮」，产出验收候选，不要凭感觉开跑。
5. 写入 `task.md` 与 `state.json`（`status=pending_confirmation`，`round=0`）。
6. 只输出**任务契约卡**（≤40 行，见 `references/templates.md`），结尾写「回复确认开始，或指出要改的条目」。
7. 用户提出修改：更新契约，回到待确认；不要边改边执行。

## 阶段二：确认门（含建立原生目标）

1. 明确确认才算：`确认 / 可以 / 按这个来 / 开始执行`。含糊回应（「嗯」「不错」）不算，追问一次。
2. 默认必须确认；只有「完全可逆 + 仅工作区内 + 影响面小」且用户明示开启自动立项时，才可跳过。
3. **确认后按顺序执行三件事，缺一不可：**
   - 把验收标准、非目标、停止条件写进原生目标的 objective（**objective 要自足**：换会话也能据它继续）。
   - 调用目标建立工具创建目标，状态 `active`。
   - 更新 `state.json`（`status=active`、记录确认时间、`native_goal_id`）并生成首版 `handoff.md`。
4. 目标建立失败：**不要静默降级**。记录失败原因到 `progress.md`，明确告知用户「未能建立自动目标，将按单指令续跑」，然后才用 L2/L3。

## 阶段三：自主执行（每轮六步）

1. **读**：只读 `state.json` + `task.md` 的验收与已决段 + `progress.md` 末 3 轮。禁止复述全历史。
2. **选**：确定本轮 `next_action`，必须一轮内可完成、有验证方式、前置已满足，并写入 `state.json`。
3. **做**：只做本轮唯一目标；写操作前记录回滚点（有版本控制记提交号，否则记备份路径）；大输出落 `evidence/`。
4. **验**：按验收项类型验证（命令退出码 / 文件断言 / 外部返回 / 人工）。失败时记录命令、关键报错、已试方案，不要原样重试。
5. **记**：更新 `state.json`、追加 `progress.md`、必要时刷新 `handoff.md`。
6. **判**：命中停止规则就停并给停止报告；否则：
   - **有原生目标**：更新目标保持 `active`，直接进入下一轮（或等系统续跑）。
   - **无原生目标**：输出续跑块。

单轮上限：1 个目标、1 次验证、≤25 次工具调用、单条命令默认超时 5 分钟（更久就转后台或拆轮）。

**不要因为「这一轮结束了」就结束目标。** 只要验收未全绿、未命中停止规则，目标就必须保持 `active`。

## 自主度与降级

按实际探测到的能力选档，**从高到低找，第一个可用的就用**：

| 档位 | 判据 | 行为 |
|---|---|---|
| L0 原生目标续跑 | 客户端有目标工具或自动续跑 | 确认后建目标；每轮维持 `active`；只在必须打断时打断 |
| L1 循环机制 | 无目标工具但有会话循环/定时机制 | 用循环指令驱动，状态文件提供每轮输入 |
| L2 单指令续跑 | 都没有，但能连续调用工具 | 单次响应内尽量推进，结束时输出续跑块 |
| L3 交接恢复 | 新会话、上下文已压缩或更换客户端 | 读 `handoff.md` 与 `state.json` 恢复，先复述再继续 |

**诚实约束**：用到 L2/L3 时必须明说「本客户端没有自动续跑，需要你说继续」。**禁止**在没建立原生目标的情况下宣称「已自动持续执行」。探测项与降级细则见 `references/clients.md`。

## 停止与阻塞（硬规则）

| 条件 | 状态文件 | 原生目标 |
|---|---|---|
| 验收全绿，人工项已确认 | `done` | `complete` |
| 连续 2 轮没有新增完成项或证据 | 换一次策略；仍无进展就汇报并停 | 保持 `active`，不算阻塞 |
| 同一阻塞连续 3 轮 | `blocked`，列出需要用户提供什么 | `blocked` |
| 轮次、时长或成本预算耗尽 | `stopped` | `budgetLimited` 或 `paused` |
| 需要超授权、不可逆操作或目标自相矛盾 | `paused` | `paused`，等用户决定 |

任何情况下都不允许无上限自动推进。**不要把「接近预算」写成阻塞**——预算类原因用预算状态，不要占用 `blocked`。

## 验证与证据

- 证据类型：命令结果、文件断言、外部返回、人工确认。人工项不得自判完成。
- 每完成一个里程碑，下一轮以评审者身份只读证据复查（不复用实现时的心智），不符就回退。
- 交付报告：验收逐条打勾 + 证据引用 + 变更清单 + 回滚点 + 遗留风险与假设。

## 授权与安全

| 操作 | 默认 |
|---|---|
| 只读分析 | 允许 |
| 工作区内写 | 允许 |
| 工作区外写、删除 | 需确认 |
| 提交、推送、发布、发消息、付费等外发或不可逆操作 | 需确认 |

不读取或传递凭据；写入不越出约定范围；预算与停止条件由用户可改。

## 上下文预算

每轮只加载状态摘要；大输出落盘、正文只留摘要；每 5 轮压缩一次 `progress.md`；不在对话里重述背景，`task.md` 是唯一事实源。**原生目标的续跑不消耗对话历史**，这正是它比对话续写更可靠的原因。

## 汇报与打断

- 正常时按里程碑汇报（验收进度 x/y、本轮证据、下一步），不要每轮长篇。
- 只有四种情况打断用户：需要决策的阻塞、需要超授权、目标有矛盾、不可逆风险。

## 反模式

- 有原生目标机制却不用，靠对话反复喊「继续」。
- 没有建立目标就宣称「已自动持续执行」。
- 建立目标后每轮结束不更新，被系统判成 idle 而断掉续跑。
- 把 objective 写成一句话标题，换会话后无法据它继续。
- 讨论还没收敛就立项开干。
- 没有可验证验收就「自主推进」。
- 一轮做多件事、一轮多次验证。
- 用「我觉得完成了」代替证据。
- 失败后原样重试。
- 无预算、无停止规则地自动推进。
- 把某个客户端的机制写成其他客户端的前提。
