# 原生目标对接与客户端降级

目标：同一套协议在任何 AI 客户端都能跑。**顺序永远是「先接管原生目标机制，再谈降级」**——降级是后备，不是默认。

## 1. 探测（立项阶段一次，写入 state.capabilities）

先从高到低找原生能力，找到就停，不要再往下判。

| 次序 | 能力 | 判定方法 | 落到 state |
|---|---|---|---|
| 1 | 目标工具 | 工具列表里有 `create_goal` / `update_goal` / `get_goal`（或同类命名） | `native_goal: {kind, create, update, get}` |
| 2 | 会话循环 | 有循环/定时/自动继续指令（如 `/loop`、`schedule`） | `loop: {kind, invoke}` |
| 3 | 命令行可续跑 | 客户端 CLI 支持对已有会话投递消息（如按 thread 投递） | `cli_queue: {cmd}` |
| 4 | 纯工具调用 | 只能连续调用工具，无上述机制 | `tools_only: true` |

**判定要动手，不要猜。** 有目标查询类工具就实际调用一次只读查询；返回正常才算可用。探测失败要记进 `progress.md`，不要静默当成没有。

## 2. 已知客户端的对接方式

表里是实测口径，客户端升级后以实际工具为准。

### Codex（`goals` 特性，stable）

- 工具：`create_goal`、`get_goal`、`update_goal`。
- 存储：`thread_goals`（objective、status）、`thread_goal_continuation_deferrals`（续跑延迟标记）。
- 状态取值：`active`、`paused`、`blocked`、`complete`，另有 `usageLimited` / `budgetLimited` 的用量与预算语义。
- 自动续跑存在，但只有目标为 `active` 且未被 deferral 挂起时才触发；被挂起时日志会出现「skipping goal continuation」。
- 可选全局预算：`goals.max_goal_token_budget`。

**关键**：`create_goal` 的 objective 必须自足；`update_goal` 用来维持 `active` 与推进进度，不要建完就不管。`blocked` 的门槛很高——同一阻塞连续三轮才算，预算类原因用预算状态，不要写成 `blocked`。

### DSH（HiMind 运行时）

- 工具：`create_goal` / `update_goal` / `get_goal`，按轮自动 continuation，有轮次上限。
- 状态：`done` / `blocked` / 预算耗尽；`blocked` 同样要求同一条件连续三轮。
- 对接：确认后 `create_goal`，每轮 `update_goal`，验收全绿才 `complete`。

### Claude Code 类

- 常用形态是会话内循环指令（`/loop <间隔> <任务>`）或持续目标类命令。
- 对接：确认后启动循环，每轮从 `state.json` 读 `next_action`；循环间隔按任务粒度选，不要过密。

### 无原生机制的客户端

落到 L2/L3，输出续跑块，并**明确告知用户需要手动说继续**。

## 3. 四档行为

**L0 原生目标（首选）**

1. 确认后立刻建目标，objective 自足。
2. 每轮结束 `update_goal` 保持 `active`，写清当前进度与下一步。
3. 只在四种情况打断：需要决策的阻塞、需超授权、目标矛盾、不可逆风险。
4. 停止时用对应终态，不要用 `paused` 代替 `complete`。

**L1 循环机制**：用循环指令驱动，每轮从状态文件取输入；循环次数上限写进 `task.md`。

**L2 单指令续跑**：单响应内尽量推进，结束输出续跑块；不得宣称后台仍在运行。

**L3 交接恢复**：读 `handoff.md` → `state.json` → `task.md` 验收段；先复述轮次与下一步再动手；状态与现状不符以证据为准修正。

能力中途变化（换客户端、目标丢失）时重新探测并更新 `capabilities`，在 `progress.md` 记一条档位变更，并由状态文件重建目标。

## 4. 目标丢失后的重建

目标可能因为会话结束、客户端重启、切换模型而消失。发现目标不存在时：

1. 先 `get_goal` 确认，不要凭猜测重建。
2. 不存在则用 `handoff.md` + `state.json` 的 `next_action` 重建，objective 带上已完成项与剩余项。
3. 向用户一行说明「目标已按第 N 轮进度重建」，不要重启任务。

## 5. 没有命令执行能力时怎么验证

1. 文件断言：读取目标文件，核对约定内容或结构。
2. 静态检查替代：用客户端自带的搜索工具检查关键符号、配置项。
3. 人工确认：写入交付报告的「人工项」，不得自判通过。
4. 缩小任务：把需要命令验证的部分拆成独立任务，等有命令能力的会话再接续。

## 6. 有后台作业能力时

- 长时执行（构建、转码、批量抓取）提交为后台作业，记录作业 ID 到 `state.json`。
- 每轮只查状态，不阻塞等待；查不到就继续做可并行的前置工作。
- 作业失败时把关键输出落 `evidence/`，再决定重试或换方案。

## 7. 跨平台命令写法

优先用客户端自带的文件、搜索、执行工具；必须写命令时给两种写法：

| 目的 | POSIX | PowerShell |
|---|---|---|
| 判断文件存在 | `test -f <path>` | `Test-Path <path>` |
| 搜索文本 | `grep -n "<文本>" <path>` | `Select-String -Path <path> -Pattern "<文本>"` |
| 列目录 | `ls -la <dir>` | `Get-ChildItem <dir> -Force` |
| 看退出码 | `echo $?` | `$LASTEXITCODE` |

不要假设有 bash；不要把绝对用户目录写进契约或状态文件，用工作区相对路径。

## 8. 续跑与控制的常用说法

| 用户说 | 技能行为 |
|---|---|
| `继续长任务 <task-id>` / `继续上次的长任务` | 走 L3 恢复，先复述再推进 |
| `汇报进度` | 只读状态，输出里程碑摘要与验收进度 |
| `暂停长任务 <task-id>` | 置 `paused`，同步原生目标，刷新交接卡 |
| `结束长任务 <task-id>` | 置 `stopped` 或 `done`，输出停止报告 |
| `为什么没有自动跑` | 检查原生目标是否存在、是否被 deferral 挂起、是否被判 idle，给出具体原因和修复动作 |

## 9. 通用注意

- 客户端可能压缩或丢弃上下文：状态文件优先，对话只作线索。
- 目标建了不更新，会被系统判成无活动而不续跑——这是「明明有目标却不动」的最常见原因。
- 工具名称各不相同：统一抽象为「建目标 / 查目标 / 更新目标 / 读 / 写 / 改 / 搜索 / 执行 / 派生子任务」，不写死工具名。
- 不确定客户端是否有某能力时：实际探测一次，按结果选档，不要猜。
