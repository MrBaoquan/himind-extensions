# 推进协议细则

## A. 立项检查表

全部满足才输出契约卡；任一项不满足就先补，不进入执行。

- [ ] 目标结果可观察、可判断达成。
- [ ] 验收至少 1 条，且每条都写了验证方式。
- [ ] 非目标已写清（至少 1 条）。
- [ ] 已决事项包含被否决方案及理由。
- [ ] 未决项 ≤3 条，且每条都有默认假设。
- [ ] 授权范围与预算明确。
- [ ] **已探测原生目标能力，结果写入 `state.capabilities`。**
- [ ] 本轮没有修改任何业务文件。

## A2. 确认后必做：装配原生目标

这是本技能能否「自己跑起来」的分水岭，逐条打勾才算交付。

- [ ] `能力确认`：确认客户端有目标工具或循环机制。
- [ ] `objective` 自足：包含目标结果、当前进度、剩余验收、非目标、停止条件；脱离对话也能读懂。
- [ ] 已调用建立工具创建目标，目标状态为 `active`。
- [ ] `state.json` 记录 `native_goal_id`、`confirmed_at`、`status=active`。
- [ ] 已生成首版 `handoff.md`。
- [ ] 若建立失败：已在 `progress.md` 记录原因，并向用户明确说明降级到 L2/L3。

**objective 写法（自足优先，不要写成标题）：**

```text
目标：<完成后可观察的结果>
当前进度：第 N 轮 / 验收 x/y
已完成：A1 ...
剩余验收：A2 <验证方式>；A3 <人工项，需用户确认>
非目标：<明确不做的事>
停止条件：验收全绿 / 连续 2 轮无进展 / 预算耗尽 / 同一阻塞连续 3 轮
状态源：<工作区>/.himind/long-tasks/<task-id>/
```

## B. 抽取六类的引导问题

自己从上下文里找答案，只对真正缺失的项提问（≤3 个问题）。

1. **目标**：做完之后，什么东西会不一样？
2. **验收**：怎么证明它成了？谁能验证、用什么验证？
3. **范围**：动哪些路径？哪些明确不碰？
4. **已决**：讨论中已经定了什么？否掉了什么、为什么？
5. **未决**：还有哪些没定？不给答案的话默认怎么处理？
6. **授权**：允许写到哪、允不允许提交、允不允许外发？

## C. 验收标准写法

| 类型 | 写法 | 验证动作 |
|---|---|---|
| 命令 | 「`<命令>` 退出码为 0」或「输出包含 `<文本>`」 | 执行并取其退出码与关键行 |
| 文件 | 「`<路径>` 中存在 `<内容>`」或「文件行数 ≤ N」 | 读取/搜索断言 |
| 外部 | 「`<接口或页面>` 返回 `<期望>`」 | 请求并记录状态与摘要 |
| 人工 | 「用户确认 `<场景>` 表现正常」 | 列入交付报告，等用户签字 |

目标无法转成以上任何一种时，第一轮做探索，产出验收候选后再进入执行。

## D. 每轮执行检查

- [ ] 只读了状态摘要，没有复述全历史。
- [ ] `next_action` 一轮内可完成。
- [ ] 写操作前已记录回滚点。
- [ ] 有可复核的验证证据。
- [ ] 已更新 `state.json` 与 `progress.md`。
- [ ] **有原生目标：已 `update_goal` 维持 `active` 并写入本轮进度；未命中停止规则不得置为终态。**
- [ ] 未超过单轮上限（1 目标 / 1 验证 / ≤25 工具调用）。

## E. 无进展与阻塞判定

- **新增完成项**：验收项由未完成变为完成。
- **新增证据**：新的、可复核的证据（重复同一输出不算）。
- **无进展轮**：两者都没有。
- **换策略**：改变方法、缩小范围或换验证手段；重复同一动作不算换策略。
- **阻塞**：需要外部输入、权限或第三方状态。同一原因第 3 轮才判定 `blocked`，第 1、2 轮先换办法。

### 与原生目标状态的对应

| 情形 | 状态文件 | 原生目标 | 说明 |
|---|---|---|---|
| 正常推进 | `active` | `active` | 每轮更新，不要漏 |
| 预算接近或耗尽 | `stopped` | `budgetLimited` / `paused` | 预算类不算阻塞 |
| 同一阻塞连续 3 轮 | `blocked` | `blocked` | 必须写明需要用户提供什么 |
| 等用户决策 | `paused` | `paused` | 不要用 `blocked` 代替 |
| 验收全绿 | `done` | `complete` | 人工项需用户确认 |

**最容易踩的坑**：目标建好后每轮不更新，系统判定该线程无活动，续跑被跳过，看起来像「有目标却不跑」。每轮结束必须更新。

## F. 压缩（每 5 轮）

1. 把第 1 至 N-5 轮合并为里程碑摘要：每 3 轮一行，写「完成什么 + 证据索引 + 遗留」。
2. 原文移入 `progress-archive.md`，`progress.md` 只留最近 5 轮。
3. `state.json` 只保留当前状态与最近一轮细节。
4. 压缩后自检：`handoff.md` 是否仍能让人只读三份文件就接上。

## G. 恢复（L3）

1. 读 `handoff.md` → `state.json` → `task.md` 的验收段。
2. 先复述「第 N 轮、阶段、下一步 X」，确认恢复点。
3. 校验一致性：验收项状态与代码/文件现状不符时，以证据为准修正 `state.json`。
4. 不重做已完成项；从 `next_action` 继续；先做一次只读核对再动手。

## H. 评审轮

里程碑完成后用一轮做评审，只读证据与验收项：

1. 逐条核对验收项与证据是否匹配。
2. 检查是否有未记录的变更或临时文件。
3. 发现不符：记为失败，写清回退动作，纳入下一轮。
4. 输出一行评审结论（通过 / 打回 + 原因）。

## I. 交付前检查

- [ ] 验收项逐条有证据，人工项已列出等用户确认。
- [ ] 变更清单完整，临时文件已清理或归档。
- [ ] 回滚点可用。
- [ ] `handoff.md` 标记 `done`，后续不再续跑。
- [ ] 交付报告含遗留风险与未决假设的最终处理。

## J. 边界情况

- **多任务并行**：一任务一目录、各自 `state.json`；同时最多 3 个，避免写面冲突。
- **目标变更**：重新立项并记 `revision`，旧契约归档，不在旧验收上打补丁。
- **用户长时间离开**：置 `paused` 并刷新 `handoff.md`；不猜测用户意图继续不可逆动作。
- **任务被证明不可行**：置 `stopped`，写清证据与替代方案，不硬撑到预算耗尽。
